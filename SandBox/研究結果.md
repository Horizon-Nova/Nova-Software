# SandBox 研究結果：免提權來源能回答「對方是誰」到什麼程度

以 ctypes 直接綁定 Win32 API，綁定形狀與 C# P/Invoke 一對一對應。全部在非提權工作階段執行。

## 已驗證可用的來源

| 模組 | API | 結果 |
|---|---|---|
| `iphlpapi.tcp_connections` | `GetExtendedTcpTable`（v4／v6 分兩次呼叫） | 113 條，含雙方位址埠、狀態、行程 |
| `iphlpapi.udp_endpoints` | `GetExtendedUdpTable` | 149 個，無遠端位址與狀態 |
| `iphlpapi.neighbors` | `GetIpNetTable2` | 453 筆，其中 234 筆有實體位址 |
| `iphlpapi.interfaces` | `GetAdaptersAddresses` | 6 張，含實體位址、速率、狀態、IP、閘道、DNS 伺服器 |
| `nameresolution.reverse` | `GetNameInfoW` | 可用；`8.8.8.8` → `dns.google` |
| `dnscache_wmi.entries` | WMI `MSFT_DNSClientCache` | 可用，含 `Data` 欄位 |

## 發現

### 一　對方的實體位址對網際網路對象恆為空

實測：75 條有遠端對象的 TCP 連線，`remote_mac` 填充率 **0/75**。

芳鄰表有 234 筆實體位址，但沒有一筆對得上連線的遠端位址。ARP／NDP 只涵蓋同一網段——網際網路對方的實體位址在協定上不存在於本機。本機芳鄰表裡的 `192.168.0.1 → FC:77:7B:7B:FB:82` 是預設閘道，是封包的下一跳，不是對方。

對「裝置」這一欄的結論：同網段對象有實體位址，網際網路對象沒有。此欄對外部連線恆為 NULL，非採集失敗。

### 二　DNS 快取涵蓋率停在兩成餘，不隨時間改善

連續觀測 60 秒：

```
t= 0s  快取筆數=83  A記錄=36  對外連線=46  具名=13  (28%)
t=10s  快取筆數=80  A記錄=40  對外連線=46  具名=11  (24%)
t=20s  快取筆數=80  A記錄=29  對外連線=48  具名=13  (27%)
t=30s  快取筆數=60  A記錄=23  對外連線=47  具名=10  (21%)
t=40s  快取筆數=59  A記錄=24  對外連線=48  具名=12  (25%)
t=50s  快取筆數=64  A記錄=29  對外連線=52  具名=14  (27%)
```

快取項目隨 TTL 消失，連線活得比它的名稱紀錄久。實例：`claude.exe → 160.79.104.10` 在一次取樣時查得 `api.anthropic.com`，數分鐘後同一條連線仍在，快取項目已消失。

輪詢快取無法可靠取得名稱。名稱必須在解析發生的當下捕捉並自行保存，不隨 TTL 消失——即 ETW DNS-Client 事件，且該事件另有 `ClientPID`，可指出是哪個行程發起解析。

### 三　`DnsQuery_W` 加 `DNS_QUERY_NO_WIRE_QUERY` 讀不到解析器快取

對快取中確實存在的名稱回傳 9701（`DNS_INFO_NO_RECORDS`）：

```
api.anthropic.com  AAAA -> 9701
api.anthropic.com  A    -> 9701
```

同時 WMI 讀得到：

```
api.anthropic.com  Type 28  2607:6bc0::10   TTL 189
api.anthropic.com  Type  1  160.79.104.10   TTL 113
```

`DnsGetCacheDataTable` 可列舉名稱與型別，但不給資料。正向對照只能走 WMI `MSFT_DNSClientCache`（C# 端為 `System.Management` 或 `Microsoft.Management.Infrastructure`）。

### 四　反向解析把涵蓋率從 27% 拉到 46%

41 條對外連線中，快取查得 11 條，反向解析再補 8 條，合計 19 條（46.3%）。過半對外連線兩種方式都查不到名稱——該位址沒有 PTR 紀錄，且其正向紀錄已過期。

反向解析為對外查詢，有網路延遲，不可在取樣輪次中同步呼叫。

### 五　`PID 0` 代表連線無擁有者

`TimeWait` 狀態的連線 `dwOwningPid` 為 0。以行程清單查詢會得到「System Idle Process」，該名稱為誤導——這些連線已無擁有行程。此欄應呈現為無值。

### 六　連線表的形狀

v4 與 v6 為兩次獨立呼叫，回傳不同結構（`MIB_TCPROW_OWNER_PID` 與 `MIB_TCP6ROW_OWNER_PID`），欄位語意相同。連接埠為網路位元組序，需取低 16 位元後轉主機序。UDP 表無遠端位址、無狀態。

## 對藍圖的修正

| 藍圖原文 | 修正 |
|---|---|
| `remote_endpoint.link_layer_address`：對方實體位址 | 僅同網段對象有值。網際網路對象恆為 NULL，此為協定事實而非採集失敗。欄位保留，語意改為「同網段對象的實體位址」。 |
| DNS 快取為名稱來源之一 | 快取為輔助，涵蓋率兩成餘且不隨時間改善。主來源為 ETW DNS-Client 事件——在解析當下捕捉、含發起行程、寫入後不隨 TTL 消失。 |
| `name_resolution.source` 值域含「快取」 | 值域為：解析事件、快取、反向解析。三者涵蓋率與可信度不同，由該欄承載，畫面可據以區分。 |
| 反向解析為來源之一 | 為對外查詢，不可在取樣輪次中同步呼叫，須另行排程。 |
| `connection.process_id` | 值為 0 時代表無擁有者，非行程 0。對照表需有此一列。 |
