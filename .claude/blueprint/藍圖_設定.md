## 定性

| 問題 | 回答 |
|---|---|
| 本質是什麼 | 一列 `app_settings`（`id` 固定為 1）的欄位讀寫，外加每個欄位變更後往哪個外部系統擴散的分派規則。欄位依擴散去向分四類：**只進資料庫**（`StartupPage`，無任何讀取端）、**資料庫＋殼層**（`ThemePackId`／`BackgroundAnimationEnabled`／`UiScalePercent`／`DataDensity`／`SidebarCollapsedByDefault`／`ShowEventBadge`）、**資料庫＋Windows**（`StartWithWindows` 走 HKCU Run 機碼；電源 8 欄走 `powercfg.exe`、HKLM `HiberbootEnabled`）、**完全不進資料庫**（`Language`／`IdleLockMinutes`／`Encoding`／`TimeZone`，只在 `SettingsViewModel` 記憶體，畫面掛「僅供展示」徽章）。畫面另外承載工作區管理與事件日誌兩個主題的欄位，本主題只呈現與觸發，不持有其資料形狀 |
| 完整生命週期是什麼 | **誕生**：App 啟動先 `EnsureCreatedAsync`，再逐欄 `EnsureColumnExistsAsync` 補齊 8 個電源欄位（既有資料庫升級路徑）；`QueryAppSettingsAsync` 查 `id=1`，查無列回傳記憶體預設物件且不落地，第一次寫入才真的建列。**單向重推**：`ApplyReconcileStartupRegistrationAsync`、`ApplyReconcilePowerSettingsAsync` 各執行一次，把持久值推到登錄檔與 Windows 電源設定，不讀系統現況、不回報結果。**執行期**：任一欄位變更即 `InsertAppSettingsAsync` 整列覆寫＋該欄對應的外部系統呼叫＋`Changed` 事件，殼層即時反映，不需重啟。**終止**：App 關閉後資料庫值與系統面值都留存，記憶體欄位消失。**反向不成立**：執行期使用者用 Windows 內建電源選項或工作管理員改動，本軟體不偵測，等下次啟動被覆寫回來 |
| 現有最小結構能否表達 | 不能：新增最小結構，理由：`powercfg.exe`／HKLM 是 `SettingsRepository`（EF Core／SQLite）與 `StartupRegistrationRepository`（HKCU）都碰不到的第三個外部系統，故新增 `PowerManagementRepository`；闔螢幕通知是視窗訊息層事件，且 ArchTests `Platform不得引用Feature` 使承載它的型別不可能放進 `Features/Settings/`，故新增 `PowerMenuRuntime`（Vaeron.Platform）＋`PowerMenuWindow`／`MainWindow` hook／`MainShellViewModel.LidCloseAction`（App 根目錄） |

## 主體順序

本藍圖採用的排序邏輯（時間／結構／重要性／演繹，四選一，全篇僅此一種）：**結構**——依 Feature 的層級依賴順序，從契約排到畫面，最後排跨出 Feature 的橫切機制。

## 骨架

本專案（WPF＋EF Core／SQLite）無 `template/` 資料夾，固定順序由既有 Feature 資料夾結構承載，逐項填寫，不可跳過、不可調換：

| 順序 | 項目 | 內容 |
|---|---|---|
| 1 | 契約 | `AppSettingsSnapshot`（16 欄位）、`DataDensity` 枚舉。跨 Feature 唯一可被引用的型別家族——ArchTests 規定 `{Feature}.Contracts` 命名空間與 `*Facade` 之外一律不得跨 Feature 引用 |
| 2 | 資料表 | `SettingsDbContext`＋`app_settings`。`id` 固定 1 的單列表；`data_density`／`power_mode`／`power_button_action`／`lid_close_action` 以字串儲存 |
| 3 | 資料庫 Repository | `SettingsRepository`：`QueryAppSettingsAsync`（查無列回記憶體預設物件，不落地）、`InsertAppSettingsAsync`（有列逐欄覆寫、無列插入） |
| 4 | 外部系統 Repository | `StartupRegistrationRepository`（HKCU `...\CurrentVersion\Run`）；`PowerManagementRepository`（`powercfg.exe` 行程呼叫＋HKLM `HiberbootEnabled` 機碼＋`SetSuspendState` P/Invoke＋`shutdown.exe`） |
| 5 | Domain | `SettingsDomain`：唯一同時持有三個 Repository 的型別，是「存檔＋外部系統呼叫＋`Changed`」的分派點。方法分兩類性質——`Apply*Async` 設定政策（供未來生效）、`Execute*NowAsync` 立即執行電源動作 |
| 6 | Facade | `SettingsFacade`：殼層（`MainShellViewModel`／`App.xaml.cs`）唯一入口，只轉呼叫與轉事件，不含邏輯 |
| 7 | DI 註冊 | `SettingsModule.AddSettingsFeature`：`SettingsDbContext` 用 `AddDbContextFactory`；三個 Repository／`SettingsDomain`／`SettingsFacade`／`ThemePackService` 為 Singleton；`SettingsViewModel`／`SettingsView` 為 Transient |
| 8 | ViewModel | `SettingsViewModel`：9 個分類的欄位屬性、關鍵字搜尋過濾、`_isApplyingSnapshot` 載入抑制旗標（載入快照時的賦值不觸發寫回） |
| 9 | View | `SettingsView.xaml`＋`SettingsConverters.cs`（9 個 Converter，全部實作 WPF 的 `IValueConverter`／`IMultiValueConverter`） |
| 10 | 跨 Feature 橫切 | `PowerMenuRuntime`（Vaeron.Platform.AppRuntime，事件無訂閱者時回 `null`＝不執行任何動作）、`PowerMenuWindow`、`MainWindow` 的 `WM_POWERBROADCAST` hook、`MainShellViewModel.LidCloseAction` |

## 技術規範遵循

| 規範 | 是否符合 | 說明 |
|---|---|---|
| 禁止 Interface | 符合 | `Features/Settings/` 與 `PowerMenuRuntime` 零自訂 interface（`grep -rn "interface " Features/Settings/` 無結果）。`SettingsConverters.cs` 實作的 `IValueConverter`／`IMultiValueConverter` 是 WPF 框架型別，不是自訂抽象 |
| DI 統一用 primary constructor | 符合 | `SettingsDomain(SettingsRepository, StartupRegistrationRepository, PowerManagementRepository)`、`SettingsFacade(SettingsDomain)`、`SettingsRepository(IDbContextFactory<SettingsDbContext>)`、`SettingsDbContext(DbContextOptions<>)` 皆為 primary constructor。`StartupRegistrationRepository`／`PowerManagementRepository`／`PowerMenuRuntime` 無建構相依，不寫建構子 |
| 是否偏離 template/ 規範（＝污染） | 偏離，刻意 | 骨架第 10 項的四個位置在 `Features/Settings/` 之外。理由：闔螢幕偵測是視窗訊息層的橫切機制，且 `PowerMenuRuntime` 位於 `Vaeron.Platform`，ArchTests `Platform不得引用Feature` 使它不可能放進 Feature 資料夾。此偏離不擴大——`PowerMenuRuntime` 只回傳使用者選了什麼，系統動作由訂閱者（`App.xaml.cs`）轉呼叫 `SettingsFacade` 執行 |

## 執行清單

| 步驟 | 動作 | 輸入 | 輸出 | 放置位置 |
|---|---|---|---|---|
| 1 | 電源 8 欄位進契約 | 畫面既有電源分類欄位 | `AppSettingsSnapshot` 新增 `PowerMode`／`AcSleepMinutes`／`BatterySleepMinutes`／`ScreenTimeoutMinutes`／`HibernateEnabled`／`FastStartupEnabled`／`PowerButtonAction`／`LidCloseAction` | `Features/Settings/Contracts/SettingsContracts.cs` |
| 2 | 單列表擴充 8 欄 | 步驟 1 的欄位與型別 | `app_settings` 新增對應欄位，字串欄以字串存 | `Features/Settings/Data/SettingsDbContext.cs` |
| 3 | 既有資料庫補欄 | 欄名／SQL 型別／預設值（`平衡`／`30`／`15`／`10`／`1`／`1`／`睡眠`／`睡眠`） | 啟動時逐欄 `EnsureColumnExistsAsync`，已存在則跳過 | `App.xaml.cs` |
| 4 | 電源系統套用點 | 單一欄位值 | 政策方法群（`powercfg /setactive`、`/change standby-timeout-ac|dc`、`/change monitor-timeout-ac` 與 `-dc`、`/hibernate on|off`、`/setacvalueindex` 與 `/setdcvalueindex SUB_BUTTONS PBUTTONACTION|LIDACTION` 後接 `/setactive SCHEME_CURRENT`、HKLM `HiberbootEnabled`）＋立即動作方法群（`ApplySleepNow`／`ApplyHibernateNow` 走 `SetSuspendState`，`ApplyShutdownNowAsync` 走 `shutdown.exe /s /t 0`），各回 `(bool success, string message)` | `Features/Settings/Data/PowerManagementRepository.cs` |
| 5 | 逐欄分派 | 單一欄位新值 | 每欄一個 `Apply*Async`：先 `LoadSettingsAsync` 組出完整快照 → `InsertAppSettingsAsync` 整列覆寫 → 只呼叫該欄對應的系統套用 → 觸發 `Changed`。「顯示關閉選單」在 `PowerButtonAction` 只存檔不呼叫系統並回傳告知訊息，在 `LidCloseAction` 則寫 `LIDACTION=0` | `Features/Settings/SettingsDomain.cs` |
| 6 | 立即動作方法群 | 選單選定的動作字串 | `ExecuteSleepNowAsync`／`ExecuteHibernateNowAsync`／`ExecuteShutdownNowAsync`，轉呼叫步驟 4 的立即動作方法，不寫資料庫 | `Features/Settings/SettingsDomain.cs` |
| 7 | 啟動單向重套 | 無 | `ReconcilePowerSettingsAsync`：讀持久值後依序套用 8 欄，任一項失敗不中斷其餘項目、不回報結果、不阻擋啟動 | `Features/Settings/SettingsDomain.cs` |
| 8 | 對外開口 | 無 | `ApplyReconcilePowerSettingsAsync`、`ApplyExecuteSleepNowAsync`／`ApplyExecuteHibernateNowAsync`／`ApplyExecuteShutdownNowAsync` | `Features/Settings/SettingsFacade.cs` |
| 9 | DI 註冊 | 無 | `services.AddSingleton<PowerManagementRepository>()` | `Features/Settings/SettingsModule.cs` |
| 10 | 電源選單事件 | 無 | `PowerMenuRuntime.ShowAsync()` 回傳 `"睡眠"`／`"休眠"`／`"關機"`／`null`；無訂閱者或取消一律 `null` | `Vaeron.Platform/AppRuntime/PowerMenuRuntime.cs` |
| 11 | 選單視窗 | 無 | `PowerMenuWindow`：`Topmost`、`WindowStartupLocation=CenterScreen`、三個動作按鈕＋取消 | `PowerMenuWindow.xaml`／`.xaml.cs` |
| 12 | 攔截闔螢幕 | 主視窗控制代碼 | `RegisterPowerSettingNotification(handle, GUID_LIDSWITCH_STATE_CHANGE, DEVICE_NOTIFY_WINDOW_HANDLE)`＋`WM_POWERBROADCAST`／`PBT_POWERSETTINGCHANGE` hook；只有 `MainShellViewModel.LidCloseAction == "顯示關閉選單"` 才往下走，其餘值直接 return | `MainWindow.xaml.cs` |
| 13 | 接上訂閱 | 無 | `PowerMenuRuntime.PowerMenuRequested += ` 開 `PowerMenuWindow`，使用者選定後轉呼叫步驟 8 的 `ApplyExecute*NowAsync` | `App.xaml.cs` |
| 14 | 啟動順序 | 無 | 開主視窗前依序 `await ApplyReconcileStartupRegistrationAsync()`、`await ApplyReconcilePowerSettingsAsync()` | `App.xaml.cs` |

## 驗收

| 項目 | 分析（我推導） | 驗證（外部系統實際跑過） |
|---|---|---|
| `SCHEME_MAX`／`SCHEME_MIN` 對應哪個電源模式 | 別名以「省電程度」命名，字面易被誤讀成效能高低 | `powercfg /setactive` 後以 `/getactivescheme` 核對：`SCHEME_MAX`＝省電、`SCHEME_MIN`＝高效能，與字面直覺相反 |
| `powercfg` 子命令是否需要系統管理員權限 | 官方文件未標註逐一命令的權限需求 | 在 `WindowsPrincipal.IsInRole(Administrator)` 回傳 `false` 的 PowerShell 實跑 `/setactive SCHEME_MAX|SCHEME_MIN|SCHEME_BALANCED`、`/change standby-timeout-ac`、`/change monitor-timeout-ac`、`/setacvalueindex` 與 `/setdcvalueindex SUB_BUTTONS PBUTTONACTION`、`/setactive SCHEME_CURRENT`，全部成功，並以 `/getactivescheme`／`/QH` 核對數值確有變更 |
| 電源按鈕「顯示關閉選單」能否攔截 | 微軟 Power Setting GUIDs 文件中，`PBUTTONACTION` 只能設定按下後執行的政策，沒有對應的事件通知 GUID | 未執行（見未驗證清單第 1 項） |
| 闔螢幕通知註冊與 hook 收訊 | 依 Power Setting GUIDs 文件，`GUID_LIDSWITCH_STATE_CHANGE` 是真實存在的通知 GUID，與電源按鈕不對稱 | 實機執行時 Windows 於註冊後自動送出一次現況通知（`lidOpen=1`），證明註冊成功且 hook 收得到訊息；另以 `SendMessage` 送出 `PBT_POWERSETTINGCHANGE`（`PowerSetting=GUID_LIDSWITCH_STATE_CHANGE`、`Data=0`），驗證 GUID 比對、Data 解析、`LidCloseAction` 判斷三者全部正確 |
| `PowerMenuWindow` 是否真的跳出 | 由步驟 13 的訂閱鏈推導 | 模擬訊息後截圖確認：標題「電源」、文字「筆電螢幕已闔上，選擇要執行的動作」、睡眠／休眠／關機三個按鈕＋取消 |
| 電源分類的成功／失敗提示是否會出現在畫面上 | `SettingsViewModel` 呼叫 `notificationRuntime.ApplyShowResult`，看起來會出現 | 全專案搜尋 `NotificationRequested`／`ConfirmRequested` 的訂閱端為零——提示不會出現在任何畫面。`PowerMenuRuntime` 因此在 `App.xaml.cs` 直接訂閱，不重蹈此模式 |
| 建置與架構測試 | 新增檔案無 `Get*` 前綴、無 `AddScoped`、無直接 `ProtectedData`／`MessageBox.Show` | 未執行（見未驗證清單第 6 項） |

未驗證清單（依賴外部系統精確行為、無法執行驗證的項目，逐條列出，是交付物的一部分）：

1. 電源按鈕被按下這個動作沒有公開事件通知 API——依微軟官方 Power Setting GUIDs 文件與社群討論推導，未以程式碼實證窮舉。推翻時要改：定性（本質的擴散去向分類）、執行清單步驟 5。
2. `powercfg /hibernate on|off` 需要系統管理員權限、非管理員時失敗——僅依公開文件推導。刻意不實測：切換會實際建立／刪除 `hiberfil.sys`，在共用開發機上有磁碟風險。推翻時要改：執行清單步驟 4、5。
3. HKLM `HiberbootEnabled` 在非系統管理員權限下寫入會擲 `UnauthorizedAccessException`——僅依 .NET `RegistryKey.OpenSubKey(writable: true)` 對 HKLM 的一般行為推導。推翻時要改：執行清單步驟 4。
4. `HiberbootEnabled` 寫入 0／1 後 Windows 是否需要重開機才生效——僅依公開文件推導，本軟體只負責寫機碼。推翻時要改：定性（完整生命週期的系統面留存描述）。
5. `/setacvalueindex`／`/setdcvalueindex` 後是否確實需要 `/setactive SCHEME_CURRENT` 才立即生效——依文件保守加上這道呼叫，未比對省略它的行為差異。推翻時要改：執行清單步驟 4。
6. `dotnet build Vaeron.HelixStudio.sln` 與 `dotnet test Vaeron.ArchTests` 未於本次執行。
7. HKCU Run 機碼寫入失敗時實際跳出的訊息內容與時機——需在權限受限環境實際觸發 `ApplyStartWithWindows` 失敗分支，僅靜態讀碼推導。推翻時要改：執行清單步驟 5 的失敗訊息判準。
8. **真實闔上筆電螢幕蓋**是否確實觸發 `GUID_LIDSWITCH_STATE_CHANGE`——已驗證的是「啟動時 Windows 自動回報現況」與「`SendMessage` 模擬訊息」兩者。刻意不測：闔蓋後看不到畫面，攔截失敗會直接進入系統預設睡眠，且闔蓋後無法用自動化工具繼續操作。推翻時要改：執行清單步驟 12。
9. `SetSuspendState` 與 `shutdown.exe /s /t 0` 被選取後是否真的執行成功——只驗證選單跳出與按鈕可點擊，未實際按下。刻意不測：會真的讓系統睡眠／休眠／關機。推翻時要改：執行清單步驟 4、6。
10. `dialog.ShowDialog()` 在 `WM_POWERBROADCAST` 處理鏈中同步跳出模組化對話框，是否會被 Windows 視為訊息處理逾時或與睡眠狀態機衝突——模擬訊息下確實跳窗且未崩潰，但未查證 Windows 對 `WM_POWERBROADCAST` 處理時間有無隱性上限。推翻時要改：執行清單步驟 11、12、13。
11. 闔螢幕跳選單時內建面板通常已關閉，使用者只有在接外接螢幕或重新打開螢幕蓋時看得到——此為「闔螢幕顯示關閉選單」概念本身的固有限制，非實作缺陷，未實機確認外接螢幕情境。推翻時要改：執行清單步驟 11。
