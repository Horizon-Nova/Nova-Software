# 工程藍圖：Helix-Studio 主視窗版面殼層（MainWindow）

## 定性

| 問題 | 回答 |
|---|---|
| 本質是什麼 | 一個獨立的 WPF 桌面應用程式殼層：頂欄（搜尋／上下頁／自訂版面配置／面板收合／事件通知）＋圖示軌導覽＋側欄佔位＋主內容佔位＋AI 助理欄＋底部狀態列，對應設計稿 `Layout.dc.html` 的完整版面結構與互動邏輯，但六個子畫面（已安裝工具／工具庫／事件日誌／設定／USB 防休眠／遠端批次傳輸）本身不在範圍內——設計稿裡這六個畫面也只是主內容區的一段虛線佔位文字，沒有實際內容。 |
| 完整生命週期是什麼 | 建立獨立專案樹（`Net/Helix-Studio/`，與 `vaeron-skeleton` 同層、完全獨立）→ 沿用 vaeron-skeleton 的 App/Feature/Kernel 分層慣例與 `Result` 型別（原始碼複製，非跨工作區參照）→ Shell Feature（Facade→Service→Logic→Store，Store 持有 nav／workspace／apps／chat 靜態種子資料）→ `ShellViewModel`（承載 `Layout.dc.html` `renderVals()` 的狀態與命令）→ WPF 資源字典（色彩、字級、圓角、欄寬取代 CSS 變數，`--ui-fluid` 公式以根層 `ScaleTransform` 重現）→ `MainWindow.xaml`（頂欄／圖示軌／側欄／主內容佔位／AI欄／狀態列）→ 建置並實際開窗驗證。 |
| 現有最小結構能否表達 | 不能：新增最小結構，理由：`Net/` 底下的既有專案樹只有 `vaeron-skeleton`，它是骨架範本本身，沒有 Helix-Studio 的畫面結構可沿用。 |

## 主體順序

本藍圖採用**結構順序**（由下而上：資料層 → 邏輯層 → 對外表面 → 組裝 → 顯示層），對應 App/Feature 分層本身由下到上被引用的方向，全篇僅此一種。

## 骨架

依 vaeron-skeleton 讀到的 App/Feature/Kernel 分層慣例延伸（此 repo 無自身 `.claude/rules/`／`template/` 文件），固定順序：

## 技術規範遵循

| 規範 | 是否符合 | 說明 |
|---|---|---|
| 禁止 Interface | 不適用 | 此 repo 無 `.claude/rules/` 規範文件，沒有「禁止 Interface」的實際規則存在——模板列這一格是通用欄位。沿用 vaeron-skeleton 本身的做法：`IShellFacade` 用 interface（比照 `IFeatureFacade`），`Internal/` 下實作類別 `internal sealed`。 |
| DI 統一用 primary constructor | 符合 | `ShellViewModel(IShellFacade facade)`、`ShellFacade(ShellService service)`、`ShellService(ShellLogic logic)`、`ShellLogic(ShellStore store)`、`App(IServiceProvider services)`、`PanelToggle(string, string, bool)` 全部主建構子。 |
| 是否偏離 template/ 規範（＝污染） | 部分偏離，逐項列出理由 | (1) 不複製 vaeron-skeleton 的 `Build/`（VAE 分析器＋Structure.targets）：該機制服務多 App 工作區的邊界問題，單一獨立專案不存在此問題，硬套是把不對應真實案例的檢查加上去。(2) `Vaeron.HelixStudio.Kernel` 只搬 `Result.cs`，不搬 `Guard`／`Paths`／`SecretBuffer`／`RegisterAttribute`／`StronglyTypedId`／`StronglyTypedIdJsonConverter`／`SafeHandleBase`／`HealthState`／`RecoveryPolicy`／`IManagedLifetime`：本殼層的 Store 只讀記憶體內靜態資料，沒有檔案／網路 I/O、沒有機密、沒有資料庫實體、沒有 P/Invoke、不是需要重試策略的常駐背景資源——移植未被使用的型別是無效果的包裝（§3.2）。此後任何畫面若需要，再依實際呼叫點移植對應那一個檔案。(3) `Vaeron.HelixStudio.Shell` 不開 `UseWPF`：ViewModel 沒有需要 `System.Windows` 型別的屬性。(4) `Internal/ShellService` 不用 try-catch 包例外轉 `Result`：全部操作是同步記憶體存取，永遠不會進入的 catch 是無效果的包裝，直接回傳 `Result.Ok(...)`。(5) 不建 `HostSetup.cs`／`appsettings.json`：本殼層沒有背景服務，`HostOptions.BackgroundServiceExceptionBehavior`／`ShutdownTimeout` 沒有作用對象；`ShellOptions` 沒有可綁定欄位，空的 `appsettings.json` 不改變任何行為。`Program.cs` 直接建 `ServiceCollection` 並以 `ValidateOnBuild`／`ValidateScopes` 建出容器，保留骨架真正有效果的那一項。 |
| 設計稿逐項對照 | 部分偏離，逐項列出理由 | (1) 頂欄右側三顆「最小化／最大化／關閉」不重繪：設計稿自己標注「原型內非功能性」，它們是瀏覽器沒有 OS 標題列時的替身；WPF 用原生視窗外框提供同樣三顆且真的能動（§5.4 先查供給）。(2) 搜尋鈕保留但不接命令：設計稿的 `focusSearch` 目標是 `apps` 畫面的搜尋框，該畫面不在本次範圍。(3) 不做 `navLoading`／`wsLoading` 骨架屏：設計稿的骨架屏覆蓋的是 `wait(700)` 人為延遲，本殼層的 Store 是同步記憶體讀取，骨架屏沒有可覆蓋的時間。(4) 不建 `Colors.Dark.xaml`：切換亮暗的入口在「設定」畫面，不在本次範圍，沒有任何路徑會載入它。(5) 面板開關色、聊天泡泡對齊與配色用 XAML `Style`／`DataTrigger` 表達：這是資料到外觀的宣告式對映，鍵是資料自身的值域（`IsOpen`、`ChatMessage.Who`），新增一種角色只多一列 `DataTrigger`，結構不動（§2.3）。 |

## 驗收

| 項目 | 分析（我推導） | 驗證（外部系統實際跑過） |
|---|---|---|
| 專案樹結構符合骨架第 1-7 項 | 逐檔比對執行清單已完成 | `dotnet build Vaeron.HelixStudio.slnx` 產出 Kernel／Shell／App 三個組件，路徑與骨架一致 |
| 建置通過 | — | 已通過：0 警告 0 錯誤（`TreatWarningsAsErrors=true`，.NET SDK 10.0.400） |
| oklch → sRGB 換算正確 | 依 Oklab 官方矩陣推導 | 換算器以 5 個已知對照色實測通過（純紅／純綠／純藍／純白／中灰各自回到 `#FF0000`／`#00FF00`／`#0000FF`／`#FFFFFF`／`#808080`） |
| `--ui-fluid` 公式與設計稿等值 | 係數 = `clamp(0.62, 0.40 + 0.015×(寬/100), 0.72)`，以 `LayoutTransform` 套在根容器 | 實測：顯示器縮放 125%、視窗 1920 物理像素 → WPF `ActualWidth` 1536 DIU → 係數 0.6304。圖示軌量得 62 物理像素（預期 80×0.6304×1.25 = 63.0），導覽項目間距量得 37.5（預期 37.7） |
| 導覽切換 | 點圖示軌項目應同時更新選中態、側欄標題、主內容佔位文字、上下頁可用狀態 | 實際點「工具庫」：四者全部同步更新，上一頁由停用轉為可用 |
| 自訂版面配置下拉 | 開啟顯示三列，勾選狀態隨區塊開關 | 實際點開：三列與快捷鍵提示（`Ctrl + B`／`Ctrl + Alt + B`／無）正確；點「狀態列」後狀態列消失、該列勾選消失且欄位槽位保留；點面板外遮罩後下拉關閉 |
| 狀態列內容 | 顯示工作區名稱／執行中數／RAM／CPU／事件數／版本 | 實際顯示「生產線 A｜執行中 2｜RAM 150 MB · CPU 3.5%｜事件 19｜v1.0.0」，與 `seed/workspaces.js` 的 `line-a` 逐欄相符 |

未驗證清單（依賴外部系統精確行為、無法執行驗證的項目，逐條列出，是交付物的一部分）：
- 換算後的顏色與設計稿在瀏覽器中的實際渲染是否肉眼相同：換算公式本身已用 5 個對照色驗證，但設計稿是 `.dc.html` 格式、需要該設計工具的執行環境才能渲染，本機無此環境，因此「兩張畫面並排比對」這件事沒有執行過。
- 設計稿導覽切換的 420ms 骨架屏延遲＋淡入位移轉場不納入本殼層：該轉場覆蓋的是子畫面內容的非同步載入時間，本殼層主內容區是一段靜態佔位文字，沒有載入可覆蓋，重現它等於加入一段純粹的人為延遲。六個子畫面接上真實內容時，轉場隨那批內容一併回來。
- 圖示軌「工具」區塊在本機實測為空：`seed/apps.js` 中 `USB 防休眠控制` 與 `遠端批次傳檔` 兩者的 `state` 都不是 `running`，過濾後沒有項目，與設計稿的初始狀態一致；但「工具啟動後該區塊會長出項目」這條路徑需要能改變工具狀態的畫面才能觸發，該畫面不在本次範圍，未實際跑過。
