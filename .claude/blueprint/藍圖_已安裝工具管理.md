依據模板版本：v1.1

| 既有藍圖 | 關係 | 說明 |

## 1. 範圍與目的

**範圍：** 已安裝工具的安裝、啟動、停止、移除、執行期狀態監控（CPU／記憶體／視窗控制代碼）、自動啟動與自動修復兩個設定欄位的鎖定與解鎖。涵蓋 `AppsManagementDomain`、`AppsManagementFacade`、`InstalledToolsRepository`、`ToolProcessRepository`、`AppsManagementDbContext`、`AppsManagementView`／`ViewModel` 全部型別。

**目的：** 讓一個工作區內已安裝的工具能被統一啟停、監控執行狀態，並對特定敏感設定欄位提供一道需要金鑰的操作門檻。

**不做什麼：**
- 不做工具的安裝來源／目錄瀏覽（由呼叫方提供完整安裝參數）
- 不做子行程的即時輸出串流顯示（僅顯示啟動／停止的結果訊息，透過事件日誌記錄）
- 不做鎖定欄位金鑰的分工具／分使用者差異化（目前是單一全域金鑰）

## 2. 主軸

**畫面上顯示的執行狀態必須忠實反映子行程當下的真實存活狀態，而不是資料庫裡「已安裝」這個靜態記錄。**

判準用法：任何提案問「它讓『畫面狀態』與『行程真實狀態』的落差更小，還是讓兩者更容易脫節」，答不出來就不屬於這個主題。

## 3. 角色

| 角色 | 身分 | 為什麼是獨立角色 |
|---|---|---|
| A. 操作者 | 在已安裝工具畫面啟停／移除／調整設定／解鎖鎖定欄位的人 | 唯一直接操作 UI 的角色，需要即時的執行狀態回饋與二次確認保護 |
| B. AppLibrary（安裝來源） | 讀取 Catalog 清單並呼叫 `InstallToolAsync` 的呼叫方 | 只在「安裝」這一個時間點接觸本主題，之後的啟停監控與自己無關，需求與操作者完全不同 |
| C. RemoteBatchTransfer／UsbVoltageControl | 依工具名稱查詢對應服務是否執行中，決定自己頁面能否送出操作 | 只需要布林結果，不需要完整快照或啟停能力 |
| D. MainShell | 讀取已安裝工具清單以顯示狀態列執行中數量 | 只讀不寫，且是全域摘要而非管理介面 |

**往底下／外面／之間找過的：**

| 角色 | 從哪裡冒出來 |
|---|---|
| 子行程本身（`Process` + `JobObjectHandle`） | 有自己獨立的生死節奏，與資料庫裡「已安裝」記錄是兩條不同的生命線，只在 `ToSnapshot` 查詢當下短暫交會 |
| 1 秒輪詢計時器 | 過場角色，持續重新查詢執行狀態，但在解鎖彈窗開啟／篩選 debounce／有列展開時主動暫停，避免打斷使用者操作 |
| 模組金鑰（硬編碼 `"000000"`） | 全域共享密鑰，不分工具、不分安裝實例 |

**收斂宣告：** 主動找過「多個工具同時啟動的資源競爭」方向——`ToolProcessRepository._running` 是以 `toolId` 為鍵的字典，各自獨立的 `Process`／`JobObjectHandle`，互不衝突，排除；也找過「解鎖狀態跨 App 重啟是否應保留」方向，`_unlockExpiry` 是記憶體字典，重啟即清空，判定為合理的安全預期而非缺口。無新方向。

### 對撞

| # | 衝突 | 標記 |
|---|---|---|
| 1 | 「執行中工具無法移除」↔「移除操作」 | 滿足——`RemoveToolAsync` 先檢查 `processRepo.IsRunning` |
| 2 | 「Error 狀態需人工排除不能重試」↔「使用者點擊啟停按鈕」 | 部分滿足——僅在 `AppsManagementViewModel.ApplyToggleStartStopAsync` 這個 UI 層擋下，`AppsManagementFacade.StartToolAsync`／`StopToolAsync` 本身沒有這個限制，任何繞過 UI 的呼叫路徑都不受保護 |
| 3 | 「鎖定欄位需金鑰解鎖」↔「解鎖機制為單一全域硬編碼字串比對」 | 衝突——`ModuleUnlockKey = "000000"` 是編譯期常數，所有工具、所有安裝共用同一組金鑰，不具備真實存取控制強度（查證後確認舊筆記此項仍成立） |
| 4 | 「1 秒輪詢更新執行狀態」↔「使用者正在篩選／解鎖／展開列」 | 滿足——`OnRefreshTick` 已排除 `UnlockPopupOpen`／`FilterLoading`／`ExpandedTool is not null` 三種情境 |
| 5 | 「`ToolRuntimeStatus` 定義 Unresponsive／Error 兩個值」↔「`GetRuntimeState` 實際邏輯」 | 衝突——`GetRuntimeState` 只依 `Process.HasExited` 與 `MainWindowHandle` 是否非零判斷，只會產生 Stopped／Starting／Running 三種結果，`Unresponsive` 與 `Error` 从未被賦值，畫面上 `ToolState.Error` 永遠不會因執行期偵測而出現，`ApplyToggleStartStopAsync` 裡 `tool.State == ToolState.Error` 恆為 false（比舊筆記「無回應未實作」描述得更精確：不只 Unresponsive，Error 整條路徑同樣是死碼） |
| 6 | 「骨架屏欄位配置」↔「實際 DataGrid 欄位」 | 不適用——查證後兩者七欄寬度與標頭完全一致（4／66／\*／58／66／92／180），舊筆記所述不一致經本次重新查證**不成立**，予以推翻 |

### 對撞產生的新需求

無 —— 對撞未產生原清單外的需求，衝突 2、3、5 屬既有實作缺口，非新需求。

### 本質

生命週期角度：「已安裝工具」有兩條並行的生命線——資料庫記錄的生死（`installed_tool.is_deleted`）與子行程的生死（`ToolProcessRepository._running` 字典，含意外結束偵測與 App 關閉時的強制清理）。兩者只在 `ToSnapshot` 查詢當下短暫交會，交會點的一致性在「移除」與「級聯清理」兩條路徑上都有主動先停止行程再處理記錄，守得住。

真正沒守住的是「執行期健康判斷」這條線：`GetRuntimeState` 從未實作偵測「行程存在但沒有回應」（例如視窗訊息幫浦逾時）或「行程存在但內部錯誤」這類語意，只判斷了「已結束」與「有沒有主視窗」。`Unresponsive`／`Error` 兩個列舉值、對應的轉換器與樣式、以及 UI 層的重試限制邏輯，管線都已接好，唯獨偵測邏輯本身缺席——這是同一個根因在三個不同層面（Domain 列舉、UI 限制、使用者可見狀態）留下的一致性缺口，不是三個獨立的小問題。

| 症狀 | 根因的哪一面 |
|---|---|
| `ToolState.Error` 永遠不會出現、「無回應」狀態未實作、UI 層對 Error 的重試限制實際上是死碼 | 執行期健康判斷邏輯本身未實作，只做了「存活／已結束」二元判斷，沒做「存活但異常」的第三種判斷 |

### 狀態

**ToolState（對外執行狀態）**

| 值 | 意義 | 進入條件 |
|---|---|---|
| Stopped | 未執行 | 無執行紀錄，或行程已結束 |
| Starting | 剛啟動、尚未偵測到主視窗且未滿 10 秒 | `Start` 成功後、`MainWindowHandle` 仍為零且啟動未滿 10 秒 |
| Running | 執行中 | 偵測到主視窗，或啟動已滿 10 秒（視為已進入穩定執行） |
| Error | 執行異常需人工排除 | 定義存在但目前無任何執行期路徑會產生此值——既有缺口 |

**ToolRuntimeStatus（內部執行期狀態，五值）**：與 `ToolState` 對應，額外有 `Unresponsive`，同樣無任何路徑會產生。

**狀態轉換：**

| 從 | 到 | 觸發 | 不可逆 |
|---|---|---|---|
| Stopped | Starting | 啟動成功 | 否 |
| Starting | Running | 偵測到主視窗或滿 10 秒 | 否 |
| Running/Starting | Stopped | 正常停止、強制終止、或行程自行結束被偵測到 | 否 |
| 已安裝（存在） | 已刪除 | 移除操作（需先確認未執行中）或工作區級聯清理 | 是 |

## 7. 失敗回饋

**失敗種類判準：重試同樣的輸入，結果會不會不同？** 會→可重試；不會→不可重試。

| 失敗 | 種類 | 使用者看到 | 呼叫方拿到 | 記事件 |
|---|---|---|---|---|
| 安裝時同工作區同名已存在 | 可重試（換名稱） | 「[失敗] 此工作區已安裝同名工具」 | `(false, message)` | 否 |
| 啟動時找不到執行檔 | 不可重試（除非重新安裝修復路徑） | 「[失敗] 找不到執行檔，工具可能未完整安裝」 | `(false, message)` | 是（Error 等級） |
| 啟動時已在執行中 | 不可重試（狀態性錯誤） | 「[失敗] 已在執行中」 | `(false, message)` | 否（此分支不記事件，只有失敗才記） |
| 停止時尚未執行 | 不可重試 | 「[失敗] 尚未執行」 | `(false, message)` | 否 |
| 移除時執行中 | 不可重試（需先停止，輸入不變則結果不變） | 「[失敗] 執行中的工具無法移除，請先停止」 | `(false, message)` | 否 |
| 更新設定時欄位鎖定且未解鎖 | 不可重試（需先解鎖） | 「[失敗] 此欄位已鎖定，請先輸入模組金鑰解鎖」 | `(false, message)` | 否 |
| 解鎖時金鑰錯誤 | 可重試（換金鑰） | 行內錯誤「金鑰錯誤，請重新輸入」 | `(false, "模組金鑰不正確")` | 否 |
| 事件記錄呼叫本身失敗（安裝／啟停／移除四處） | 不可重試 | 無專屬訊息——例外沿呼叫鏈往上拋，主操作（如安裝）已完成的結果會被這個例外蓋過 | 未被捕捉的例外 | 沿用藍圖_事件日誌.md 已記錄的既有缺口 |

**貫穿規則：** 所有訊息一律以 `ResultContract` 的 `Ok`／`Fail`（`"[失敗] "` 前綴）產生；`Error` 狀態的「需人工排除」限制目前只存在於 UI 層，Facade 本身不擋。

| 列展開細節 | 摘要 tab（開發者／描述）與設定 tab（自動啟動／自動修復切換，鎖定時顯示鎖頭圖示與解鎖倒數） |
| 解鎖 Modal | 全螢幕遮罩＋金鑰輸入框＋行內錯誤訊息 |

### 狀態呈現

| 狀態 | 視覺 |
|---|---|
| Stopped | 對應 `ToolStateToBrushConverter` 之顏色與徽章文字 |
| Starting | 同上，不同顏色 |
| Running | 同上，不同顏色 |
| Error | 同上，不同顏色——但實務上此視覺永遠不會因執行期偵測觸發 |
| 操作進行中（Pending） | 骨架列樣式取代狀態徽章／CPU／記憶體／上次啟動／操作按鈕欄位 |
| 剛完成操作 | 該列背景短暫變色（閃爍效果），700ms 後恢復 |
| 鎖定欄位 | 鎖頭圖示＋降低不透明度 |

### 空狀態與過渡

| 情境 | 呈現 |
|---|---|
| 無資料 | 與「篩選後無結果」共用同一句「沒有符合條件的工具」 |
| 過濾後無結果 | 同上 |
| 載入中 | 骨架屏（`TableSkeletonView`，5 列，欄位配置與實際表格七欄一致——經查證無不一致，推翻舊筆記） |
| 載入失敗 | 無本主題專屬呈現，依賴全域未處理例外機制 |
| 篩選 debounce 過渡 | 420ms 內顯示骨架屏，避免逐字觸發查詢造成畫面閃爍 |
| 切換工作區 | 觸發重新載入（`OnWorkspaceChanged` → `ApplyReloadCoreAsync`），顯示骨架屏含最短可視時間 400ms |

### 互動限制

| 限制 | 內容 |
|---|---|
| Error 狀態 | UI 層擋下啟停按鈕的重試（見對撞 2），但此狀態實務上不會出現 |
| 執行中工具 | 移除按鈕停用 |
| 有列展開或篩選中或解鎖彈窗開啟 | 1 秒輪詢暫停，避免打斷操作 |
| 展開列 | 同時只能展開一列 |

## 9. 行為規格

> 逐項對應第 5 段，數量一致。

### 對應第 5 段第 1 項：查詢已安裝工具清單

| 情境 | 條件 | 該發生什麼 |
|---|---|---|
| 正常 | 工作區存在已安裝工具 | 依名稱排序回傳，附即時執行狀態 |
| 邊界 | 工作區無已安裝工具 | 回傳空清單 |
| 邊界 | 行程已在背景結束但尚未被查詢觸發清理 | 下一次 `GetRuntimeState` 呼叫時偵測到 `HasExited`，即時清出 `_running` 並回傳 Stopped |

### 對應第 5 段第 2 項：安裝工具

| 情境 | 條件 | 該發生什麼 |
|---|---|---|
| 正常 | 名稱不重複 | 寫入成功，記一筆 Info 事件 |
| 異常 | 同工作區同名已存在 | 回傳失敗，不寫入，不記事件 |

### 對應第 5 段第 3 項：啟動工具

| 情境 | 條件 | 該發生什麼 |
|---|---|---|
| 正常 | 執行檔存在且未在執行中 | 建立子行程與 Job Object，記 Info 事件 |
| 異常 | 執行檔不存在 | 回傳失敗，記 Error 事件 |
| 異常 | 已在執行中 | 回傳失敗，不記事件 |
| 邊界 | 找不到該工具 id | 回傳「找不到該工具」，不記事件 |
| 邊界 | 啟動後 10 秒內未偵測到主視窗 | 狀態維持 Starting，超過 10 秒後即使無主視窗也視為 Running |

### 對應第 5 段第 4 項：停止工具

| 情境 | 條件 | 該發生什麼 |
|---|---|---|
| 正常 | 正常關閉在 3 秒內完成 | 記 Info 事件「已停止」 |
| 異常 | 3 秒內未正常結束 | 透過 Job Object 強制終止全部子行程，仍記為停止完成 |
| 異常 | 尚未執行 | 回傳失敗「尚未執行」，不記事件 |

### 對應第 5 段第 5 項：移除工具

| 情境 | 條件 | 該發生什麼 |
|---|---|---|
| 正常 | 未執行中且 id 存在 | 軟刪除，記 Info 事件「已移除」 |
| 異常 | 執行中 | 直接擋下，不查詢也不刪除 |
| 邊界 | id 不存在 | 回傳「找不到該工具」 |

### 對應第 5 段第 6 項：更新自動啟動／自動修復設定

| 情境 | 條件 | 該發生什麼 |
|---|---|---|
| 正常 | 欄位未鎖定，或已解鎖 | 覆寫成功 |
| 異常 | 欄位鎖定且未解鎖且新值與現值不同 | 回傳失敗，不覆寫 |
| 邊界 | 欄位鎖定但新值與現值相同 | 視為未變更，允許通過（程式碼以 `!= tool.auto_start` 判斷差異才擋） |

### 對應第 5 段第 7 項：解鎖鎖定欄位

| 情境 | 條件 | 該發生什麼 |
|---|---|---|
| 正常 | 金鑰等於 `"000000"` | 給予該工具 id 3 分鐘解鎖期限 |
| 異常 | 金鑰錯誤 | 回傳失敗，不給予解鎖期限 |
| 邊界 | 解鎖期限到期後再次操作鎖定欄位 | `IsUnlocked` 重新計算為 false，需再次輸入金鑰 |

### 對應第 5 段第 8 項：依名稱查詢是否執行中

| 情境 | 條件 | 該發生什麼 |
|---|---|---|
| 正常 | 該名稱工具存在且執行中 | 回傳 true |
| 邊界 | 該名稱不存在，或存在但未執行 | 回傳 false |

### 對應第 5 段第 9 項：刪除工作區時清理已安裝工具

| 情境 | 條件 | 該發生什麼 |
|---|---|---|
| 正常 | 該工作區有執行中的工具 | 先逐一停止，再批次軟刪除全部安裝記錄 |
| 邊界 | 該工作區無任何已安裝工具 | 批次刪除影響 0 筆，不視為錯誤 |

**跨操作互動：** 啟停／移除進行中該列會標記 Pending 並停用操作按鈕（`_pendingToolIds`），避免同一列被重複觸發；1 秒輪詢在解鎖彈窗、篩選、展開列時暫停，其餘時間持續刷新执行狀態。

## 10. 判準

| 判準 | 適用情境 |
|---|---|
| Error 狀態的「需人工排除」限制只在 UI 層存在，Facade 本身不擋 | 任何討論「能否繞過 UI 直接呼叫啟停」的前提 |
| 模組解鎖金鑰是全域單一硬編碼字串，不分工具 | 任何討論鎖定欄位安全強度的前提 |
| `ToolState.Error` 與 `Unresponsive` 目前無任何執行期路徑會產生 | 任何依賴這兩個狀態做判斷或測試的前提，需先知道這是死碼 |
| 解鎖狀態為記憶體字典，App 重啟即清空 | 任何討論「解鎖是否應跨重啟保留」的前提，答案是刻意不保留 |
| 骨架屏欄位配置與實際表格欄位一致 | 舊筆記所述不一致已查證推翻，不需要修正 |

## 11. 驗收條件

| # | 條件 | 怎麼證明 |
|---|---|---|
| 1 | 建置通過 | `dotnet build` 對 `Vaeron.HelixStudio.sln` 成功 |
| 2 | 執行中工具無法移除 | 手動操作：啟動一個工具後點擊移除，預期收到「[失敗] 執行中的工具無法移除，請先停止」 |
| 3 | 安裝同名工具被擋 | 手動操作：對同一工作區安裝兩次同名工具，預期第二次收到「[失敗] 此工作區已安裝同名工具」 |
| 4 | 鎖定欄位解鎖後 3 分鐘失效 | 手動操作：解鎖後等待超過 3 分鐘再次點擊鎖定欄位，預期需要重新輸入金鑰 |
| 5 | 刪除工作區時執行中工具被先停止 | 手動操作：在有執行中工具的工作區觸發刪除，預期對應子行程被終止且安裝記錄消失 |

### 未驗證的推測

| 項目 | 為什麼未驗證 | 若推測錯誤要改哪幾段 |
|---|---|---|
| `GetRuntimeState` 的 10 秒門檻（Starting → Running）在實際慢啟動的工具上是否會誤判為 Running | 需要實際跑一個啟動緩慢、10 秒內仍無主視窗的工具觀察行為，本次僅靜態讀碼推導 | 6（狀態轉換）、9（啟動工具的邊界情境） |
| Job Object 強制終止（`TerminateAll`）在子行程有孫行程時的實際清理範圍 | 需要實際啟動會建立子行程的工具並觀察行程樹是否被完整清理，屬 Windows 執行期行為 | 9（停止工具的異常情境） |

無其餘未驗證項目——本藍圖其餘結論均可由現有原始碼靜態查證。
