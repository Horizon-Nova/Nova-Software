# 工程藍圖：工作區管理

依據模板版本：v1.1

## 0. 依據與關係

| 既有藍圖 | 關係 | 說明 |
|---|---|---|
| 無 | 無相關 | `.claude/blueprint/` 現存內容於本藍圖撰寫前已遺失且無法從 git 復原（`.claude/` 未受版控），本藍圖為重新查證程式碼後的首份藍圖，不沿用任何舊文件內容 |

## 1. 範圍與目的

**範圍：** 工作區（產線）的建立、改名、刪除、切換、查詢，以及「目前作用中工作區」這個全域單例狀態的讀寫。涵蓋 `WorkspaceManagementDomain`、`WorkspaceManagementFacade`、`WorkspaceManagementRepository`、`WorkspaceManagementDbContext` 四個型別。不含任何畫面——畫面由呼叫方承載。

**目的：** 讓多條產線／多個獨立作業環境在同一份安裝下彼此隔離資料（各自的已安裝工具、各自的事件記錄），且任一時刻只有一個是「作用中」。

**不做什麼：**
- 不做工作區資料的實體匯出／匯入
- 不做工作區層級的權限或存取控制（單一操作者假設）
- 不做多個作用中工作區（同時只能有一個）

## 2. 主軸

**任一時刻資料庫裡恰好存在一個「作用中工作區」，且這個狀態的讀寫是本主題唯一的真實來源。**

判準用法：任何提案問「它讓『恰好一個作用中工作區』這件事更成立、還是更容易被破壞」，答不出來就不屬於這個主題。

## 3. 角色

| 角色 | 身分 | 為什麼是獨立角色 |
|---|---|---|
| A. 操作者 | 在設定畫面管理工作區清單的人 | 需要 CRUD 與切換，且承受「至少保留一個」「刪除需二次確認」這些限制 |
| B. 全域殼層消費者 | 讀取 active workspace 以驅動狀態列、切換下拉、其他 Feature 的資料範圍 | 只讀不寫（除了觸發切換命令），需要的是「馬上知道現在是哪一個」而非管理介面 |

**往底下／外面／之間找過的：**

| 角色 | 從哪裡冒出來 |
|---|---|
| SQLite（經 `IDbContextFactory<WorkspaceManagementDbContext>`） | 唯一持久層，`workspace`／`active_workspace` 兩張表；資料庫檔案路徑由 `AppDataPath.DatabasePath` 決定，本主題不擁有這個決策 |
| EventLogFacade／AppsManagementFacade（下游被通知者） | 刪除工作區時被級聯呼叫清除對應資料，依賴方向與一般「被依賴」相反——本主題主動呼叫它們 |
| `WorkspaceChanged` 事件訂閱者們 | Settings 與 MainShell 各自獨立訂閱、各自刷新，屬於過場時機角色，不持有狀態 |

**收斂宣告：** 主動找過「多執行緒/多操作者並發寫入」這個方向——桌面應用單一 UI 執行緒、單一操作者，資料庫沒有版本欄位或樂觀鎖，判定不適用；也找過「工作區層級權限」方向，程式碼與畫面均無此概念，排除。無新方向。

## 4. 需求

| 角色 | 會用到 | 需要 | 工作會用到 | 想要 |
|---|---|---|---|---|
| A 操作者 | 新增／改名／刪除／切換／清單顯示 | 名稱重複要擋、至少保留一個工作區、刪除要二次確認 | 依產線分工建立多個工作區，各自累積工具安裝與事件記錄 | 一眼看出哪個是目前作用中的 |
| B 全域殼層消費者 | 讀 active workspace、讀清單、訂閱變更事件 | 切換命令要能回報成功/失敗訊息 | 狀態列、切換下拉、其他 Feature 依 workspace id 篩資料 | 資料異動時被動收到通知，不用輪詢 |

### 對撞

| # | 衝突 | 標記 |
|---|---|---|
| 1 | 「至少保留一個工作區」↔「刪除工作區」 | 滿足——`CountWorkspacesAsync <= 1` 時直接擋在 Domain 層 |
| 2 | 「刪除工作區」↔「該工作區恰為 active」 | 滿足——`DeleteWorkspaceAndReassignActiveAsync` 於同一交易內重新指派下一個（依名稱排序） |
| 3 | 「名稱唯一性」↔「改名為自己原本的名稱」 | 滿足——`ExistsWorkspaceAsync` 以 `excludeId` 排除自身 |
| 4 | 「刪除工作區」↔「級聯清除 EventLog／AppsManagement 資料」 | 衝突——三個操作跨兩個獨立 DbContext，無法包在同一交易 |
| 5 | Settings 與 MainShell 各自訂閱 `WorkspaceChanged` | 不適用——各自獨立刷新，互不影響 |

### 對撞產生的新需求

無 —— 對撞未產生原清單外的需求，衝突 4 屬於既有實作的一致性缺口，非新需求。

### 本質

生命週期角度：工作區的死亡是軟刪除（`is_deleted = true`），死亡本身在自己的資料表交易內是原子的；但死亡會「拖累」EventLog 與 AppsManagement 兩個下游 Feature 的資料清理，而這段拖累沒有交易保護、沒有補償/重試機制——刪除主表成功後若下游清除擲出例外，會留下指向已刪除 workspace id 的孤兒事件/工具紀錄。

| 症狀 | 根因的哪一面 |
|---|---|
| 刪除工作區中途失敗會留孤兒資料 | 級聯刪除跨 Feature 邊界執行，卻沒有跨邊界的一致性保護——這是架構層的缺口，不是這次要修的 bug，但寫進第 9 段與第 11 段留下可查證的紀錄 |

## 5. 功能清單

| # | 操作 | 觸發方式 | 做什麼 |
|---|---|---|---|
| 1 | 查詢工作區清單 | 載入／外部呼叫 | 回傳未刪除工作區，依名稱排序，附是否為 active |
| 2 | 查詢作用中工作區 | 載入／外部呼叫 | 回傳目前 active 的工作區快照，無則回傳 null |
| 3 | 新增工作區 | 按鈕 | 驗證名稱唯一後寫入；若是第一筆，同一交易內自動設為 active |
| 4 | 改名工作區 | 按鈕 | 驗證名稱唯一（排除自己）後更新名稱／描述 |
| 5 | 刪除工作區 | 按鈕（需前端二次確認） | 軟刪除＋若刪的是 active 則重新指派＋級聯清除下游兩個 Feature 的資料 |
| 6 | 切換作用中工作區 | 按鈕 | 將 `active_workspace` 單列指向目標 id |

## 6. 資料與狀態

### 資料形狀

**WorkspaceSnapshot（對外契約）**

| 欄位 | 型別 | 必填 | 約束 |
|---|---|---|---|
| Id | int | 是 | 對應 `workspace.id` |
| Name | string | 是 | 未刪除工作區間唯一 |
| Description | string | 是 | 可為空字串，不可為 null |
| CreatedAt | DateTimeOffset | 是 | 建立時寫入，UTC，不可變 |
| IsActive | bool | 是 | 由查詢當下與 active_workspace 比對得出，非持久欄位 |

**CreateWorkspaceRequest**

| 欄位 | 型別 | 必填 | 約束 |
|---|---|---|---|
| Name | string | 是 | 不可與現存未刪除工作區重複 |
| Description | string | 否 | 預設空字串 |

**RenameWorkspaceRequest**

| 欄位 | 型別 | 必填 | 約束 |
|---|---|---|---|
| Id | int | 是 | 目標必須存在且未刪除 |
| Name | string | 是 | 不可與其他未刪除工作區重複（排除自己） |
| Description | string | 否 | 預設空字串 |

**workspace（內部資料表）**

| 欄位 | 型別 | 必填 | 約束 |
|---|---|---|---|
| id | int | 是 | 主鍵 |
| name | string | 是 | 預設空字串起始 |
| description | string | 是 | 預設空字串 |
| created_at | DateTimeOffset | 是 | 建立時寫死，不可變 |
| is_deleted | bool | 是 | 軟刪除旗標，預設 false |

**active_workspace（內部單列表）**

| 欄位 | 型別 | 必填 | 約束 |
|---|---|---|---|
| id | int | 是 | 固定為 1，全表僅此一列 |
| workspace_id | int | 是 | 指向目前作用中的 `workspace.id` |

### 狀態

**工作區存續狀態**

| 值 | 意義 | 進入條件 |
|---|---|---|
| 存在且非 active | 一般工作區 | 建立且非首筆，或曾為 active 但已被切走 |
| 存在且 active | 目前作用中 | 建立為首筆，或被 `SwitchActiveWorkspaceAsync` 指定，或原 active 被刪除後系統自動指派 |
| 已刪除 | `is_deleted = true`，查詢一律排除 | 執行刪除操作 |

**狀態轉換：**

| 從 | 到 | 觸發 | 不可逆 |
|---|---|---|---|
| 不存在 | 存在且非 active（或首筆時為 active） | 新增 | 否 |
| 存在且非 active | 存在且 active | 切換 | 否 |
| 存在且 active | 存在且非 active | 另一工作區被切換為 active | 否 |
| 存在且 active | 已刪除＋另一工作區被系統指派為 active | 刪除（且刪的是目前 active、且尚有其他工作區） | 是 |
| 存在且非 active | 已刪除 | 刪除 | 是 |

### 讀寫

| 操作 | 讀 | 寫 |
|---|---|---|
| 查詢清單 | `workspace`（未刪除）＋`active_workspace` | 無 |
| 查詢作用中 | `active_workspace`＋`workspace` | 無 |
| 新增 | `workspace`（名稱唯一性檢查） | `workspace` 新增列；若為首筆，`active_workspace` 寫入 |
| 改名 | `workspace`（名稱唯一性檢查，排除自己） | `workspace.name`／`description` |
| 刪除 | `workspace`／`active_workspace`／目前工作區數量 | `workspace.is_deleted`；若刪的是 active，`active_workspace.workspace_id` 改指下一個；另外呼叫 EventLog／AppsManagement 各自的刪除清除 |
| 切換 | `workspace`（確認目標存在） | `active_workspace.workspace_id` |

### 對外能力

| 能力 | 輸入 | 輸出 |
|---|---|---|
| 取得工作區清單 | 無 | `IReadOnlyList<WorkspaceSnapshot>` |
| 取得作用中工作區 | 無 | `WorkspaceSnapshot?` |
| 建立工作區 | `CreateWorkspaceRequest` | `(success, message)` |
| 改名工作區 | `RenameWorkspaceRequest` | `(success, message)` |
| 刪除工作區 | 工作區 id | `(success, message)` |
| 切換作用中工作區 | 工作區 id | `(success, message)` |
| 訂閱異動通知 | 無（事件訂閱） | 工作區清單或作用中對象發生任何異動時觸發，不附帶異動內容，訂閱者需自行重新查詢 |

## 7. 失敗回饋

**失敗種類判準：重試同樣的輸入，結果會不會不同？** 會→可重試；不會→不可重試。

| 失敗 | 種類 | 使用者看到 | 呼叫方拿到 | 記事件 |
|---|---|---|---|---|
| 新增／改名時名稱重複 | 可重試（換名稱即可成功） | 「[失敗] 名稱已存在」 | `(false, message)` | 否 |
| 刪除時僅剩一個工作區 | 不可重試（除非先新增別的工作區，輸入本身不變結果不變） | 「[失敗] 至少要保留一個工作區」 | `(false, message)` | 否 |
| 改名／刪除／切換對象已不存在（id 失效） | 不可重試 | 「[失敗] 找不到該工作區」 | `(false, message)` | 否 |
| 級聯清除下游資料時擲出例外 | 不可重試（資料狀態已部分變更） | 無使用者可見訊息——例外會中斷 `DeleteWorkspaceAsync` 呼叫鏈，前端 `notificationRuntime` 不會收到明確訊息 | 未被捕捉的例外 | 是——屬既有缺口，目前程式碼未捕捉此例外並記事件，應在修復時補上 |

**貫穿規則：** 所有失敗訊息一律以 `ResultContract.FailPrefix`（`"[失敗] "`）開頭，呼叫方與畫面不得自行組字串。

## 8. 前端設計

無 —— 本主題不含畫面，只提供對外能力；工作區 CRUD 畫面由 Settings 承載（「工作區（產線）管理」分類），作用中工作區顯示與切換下拉由 MainShell 承載。

## 9. 行為規格

> 逐項對應第 5 段，數量一致。

### 對應第 5 段第 1 項：查詢工作區清單

| 情境 | 條件 | 該發生什麼 |
|---|---|---|
| 正常 | 存在未刪除工作區 | 依名稱排序回傳，`IsActive` 依 `active_workspace` 比對標記 |
| 邊界 | 全部工作區皆被刪除（理論上不會發生，見判準） | 回傳空清單 |

### 對應第 5 段第 2 項：查詢作用中工作區

| 情境 | 條件 | 該發生什麼 |
|---|---|---|
| 正常 | `active_workspace` 指向存在的未刪除工作區 | 回傳該工作區快照，`IsActive = true` |
| 邊界 | `active_workspace` 表尚無任何列（全新安裝、尚未建立過工作區） | 回傳 `null` |

### 對應第 5 段第 3 項：新增工作區

| 情境 | 條件 | 該發生什麼 |
|---|---|---|
| 正常 | 名稱不重複 | 建立成功；若非首筆，active 不變 |
| 正常 | 名稱不重複且為首筆 | 建立成功並於同一交易內自動設為 active |
| 異常 | 名稱與現存未刪除工作區重複 | 回傳失敗，不寫入 |
| 邊界 | 名稱為空字串 | Domain 層未擋，會直接嘗試唯一性檢查並可能建立空名稱工作區——屬既有缺口，未做非空驗證 |

### 對應第 5 段第 4 項：改名工作區

| 情境 | 條件 | 該發生什麼 |
|---|---|---|
| 正常 | 新名稱不與其他工作區重複 | 更新成功 |
| 異常 | 新名稱與其他工作區重複 | 回傳失敗，不更新 |
| 邊界 | 目標 id 已被刪除或不存在 | 回傳「找不到該工作區」 |

### 對應第 5 段第 5 項：刪除工作區

| 情境 | 條件 | 該發生什麼 |
|---|---|---|
| 正常 | 尚有其他工作區、刪的不是 active | 軟刪除成功，級聯清除下游資料 |
| 正常 | 尚有其他工作區、刪的是 active | 軟刪除成功，同交易內重新指派下一個（依名稱排序）為 active，再級聯清除下游資料 |
| 異常 | 目前僅剩一個工作區 | 直接擋下，不執行任何刪除 |
| 異常 | 目標 id 不存在 | 回傳「找不到該工作區」 |
| 邊界 | 級聯清除下游其中一個 Feature 時擲出例外 | 主表已完成軟刪除且已提交，下游清除中斷——既有缺口，無回滾、無補償 |

**跨操作互動：** 刪除進行中，本主題自身無鎖定機制阻止同時發起另一次刪除或切換；桌面單一 UI 執行緒下不會真的並發，判定不需處理。

### 對應第 5 段第 6 項：切換作用中工作區

| 情境 | 條件 | 該發生什麼 |
|---|---|---|
| 正常 | 目標工作區存在 | `active_workspace` 指向目標，觸發 `WorkspaceChanged` |
| 異常 | 目標工作區不存在或已刪除 | 回傳「找不到該工作區」，不變更 |

## 10. 判準

| 判準 | 適用情境 |
|---|---|
| 刪除操作永遠不允許將工作區數量降到 0 | 任何刪除請求，不論是否為 active |
| 名稱唯一性檢查一律排除自身 id | 改名操作 |
| 刪除 active 工作區時，重新指派的對象固定取「依名稱排序後第一個未刪除工作區」 | 刪除操作且目標為 active |
| 級聯清除順序固定為先 EventLog 後 AppsManagement，兩者之間目前無交易保護 | 刪除操作實作與缺口追蹤 |

## 11. 驗收條件

| # | 條件 | 怎麼證明 |
|---|---|---|
| 1 | 建置通過 | `dotnet build` 對 `Vaeron.HelixStudio.sln` 成功 |
| 2 | 新增／改名重複名稱時擋下 | 手動操作：對同一工作區清單新增或改名為既有名稱，預期收到「[失敗] 名稱已存在」 |
| 3 | 僅剩一個工作區時刪除被擋下 | 手動操作：清空到剩一個後嘗試刪除，預期收到「[失敗] 至少要保留一個工作區」 |
| 4 | 刪除 active 工作區後自動重新指派 | 手動操作：刪除目前 active 的工作區（尚有其他工作區時），預期另一工作區變為 active 且為名稱排序後第一個 |
| 5 | 切換後 `WorkspaceChanged` 觸發，Settings／MainShell 畫面同步刷新 | 實際操作 UI 觀察兩處畫面是否同時更新 |

### 未驗證的推測

| 項目 | 為什麼未驗證 | 若推測錯誤要改哪幾段 |
|---|---|---|
| 級聯清除下游擲出例外時的實際使用者可見行為（是否有全域例外處理攔截並顯示訊息） | 需要實際觸發下游例外（例如讓 EventLog 資料庫檔案被鎖住）並觀察執行期行為，本次僅靜態讀碼推導 | 7（失敗回饋）、9（刪除工作區的邊界情境） |
| 多個 `IDbContextFactory` 建立的 SQLite 連線在刪除交易與下游清除之間是否有檔案鎖競爭 | 需要實際併發執行才能觀察，SQLite 檔案鎖行為未實測 | 9（跨操作互動）、10 |

無其餘未驗證項目——本藍圖其餘結論均可由現有原始碼靜態查證。
