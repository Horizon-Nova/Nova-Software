# 工程藍圖：事件日誌

依據模板版本：v1.1

## 0. 依據與關係

| 既有藍圖 | 關係 | 說明 |
|---|---|---|
| 藍圖_工作區管理.md | 沿用 | 沿用其「刪除工作區時級聯清除下游 Feature 資料，跨 DbContext 無交易保護」的既有缺口描述——本主題的 `DeleteEventsByWorkspaceAsync` 正是被級聯呼叫的下游之一 |

## 1. 範圍與目的

**範圍：** 事件記錄的寫入、查詢、篩選、標記已讀、日誌等級與保留期限設定、依保留期限清理過期記錄。涵蓋 `EventLogDomain`、`EventLogFacade`、`EventLogRepository`、`EventLogDbContext`、`EventLogView`／`EventLogViewModel` 五組型別。

**目的：** 讓工具安裝／啟動／停止等操作留下可回溯的歷史紀錄，供故障排查使用；讓使用者能依嚴重度與時間範圍縮小範圍找到需要的記錄。

**不做什麼：**
- 不做單筆事件的手動刪除
- 不做事件記錄的即時推播（新事件只在下次查詢或 `Changed` 事件觸發重新整理時可見）
- 不做跨工作區的事件記錄查詢（每次查詢固定綁定單一 workspace_id，保留期限清理例外——見第 9 段）

## 2. 主軸

**事件有兩種誕生方式：角色 B（手動記錄方）寫入時要通過 `MinLevel` 門檻；FacadeAuditProxy 自動攔截寫入額外固定排除 Info（成功的 Function 之間互動），Warning／Error 之上再套用同一個 `MinLevel` 門檻。兩條路徑各自獨立、互不依賴、互不阻擋，但共用同一套嚴重度分層與同一個 `MinLevel` 設定值——不是「自動攔截取代手動記錄」，也不是「兩者疊加成單一判斷函式」。**

背景：原設計唯一的寫入入口是角色 B 手動呼叫 `RecordEventAsync`，門檻在那個入口把關是刻意設計。後來新增自動攔截（`FacadeAuditProxy` → `EventLogAuditSink` → `EventLogService.RecordAutomaticEventAsync`），目的是「不管有沒有人手動呼叫，操作本身自動留痕」，當時的實作讓角色 C 完全繞過門檻——這在角色 C 剛上線、資料量還小時沒造成問題，但角色 C 攔截的是全部 7 個 Feature 的全部 Facade 方法呼叫，絕大多數是成功的 Function 之間互動（Info），長期執行下 EventLog 資料庫被大量無意義的成功呼叫記錄淹沒，使用者實際需要查的失敗／異常訊號反而被稀釋。後改為：角色 C 固定排除 Info（不管 `MinLevel` 設多低都不會把成功呼叫寫進資料庫），Warning／Error 則額外遵守使用者於「設定 > 日誌」設定的 `MinLevel`（例如設為 Error 時，角色 C 也只留 Error）。本地文字檔（`AuditLogging`）路徑完全不受此變更影響，仍捕捉全部呼叫——收斂只發生在 EventLog 資料庫這一條路徑上。

判準用法：任何提案問「它是否讓 EventLog 資料庫只保留使用者需要回溯的訊號（角色 B 手動事件、角色 C 的 Warning／Error），還是又把純粹的成功 Function 呼叫（Info）塞回資料庫」，答不出來就不屬於這個主題。

## 3. 角色

| 角色 | 身分 | 為什麼是獨立角色 |
|---|---|---|
| A. 檢視操作者 | 在事件日誌畫面搜尋／篩選／展開／複製，或在設定畫面調整日誌等級與保留期限的人 | 需要的是「找得到、看得懂」，不涉及寫入 |
| B. 事件寫入方 | AppsManagement／RemoteBatchTransfer／UsbVoltageControl 三個 Feature 的 Domain，呼叫 `RecordEventAsync` 記錄工具生命週期事件 | 全部呼叫點都是 fire-and-forget：`await` 但不檢查回傳的 `(success, message)`，需求與檢視操作者完全不同——只要求「寫得進去」 |
| C. 自動攔截寫入方 | `FacadeAuditProxy`（`Vaeron.HelixStudio.Internal.Runtime`）——包住全部 7 個 Feature 的每一個公開 Facade 介面，每次方法呼叫（成功／`Result.Fail`／例外）自動觸發一次 `EventLogAuditSink.CaptureAsync` | 不是「呼叫」而是「攔截」：業務程式碼完全不知道這件事在發生，連事件記錄的存在都不需要知道；需求是「有意義的操作自動留痕，不依賴任何人記得呼叫」，與角色 B 的「主動呼叫、可控制內容」不同——但兩者都認同「純粹成功的 Function 呼叫不是使用者要的訊號」這一點 |

**往底下／外面／之間找過的：**

| 角色 | 從哪裡冒出來 |
|---|---|
| App 啟動流程（`App.xaml.cs`） | 保留期限清理（`ApplyRetentionPolicyAsync`）唯一的觸發點，只在應用程式啟動時執行一次，不是持續背景排程 |
| SQLite（`events`／`log_settings_rows`／`read_markers` 三表） | 唯一持久層 |
| 全域未處理例外處理器（`ViewModelBase.UnhandledAsyncError`） | 攔截 `RunSafe` 包住的例外並顯示通用訊息「[失敗] 資料載入失敗」——但事件寫入方（角色 B）呼叫 `RecordEventAsync` 時完全沒有 try/catch，例外不經過這層，會直接中斷呼叫方自己的方法執行 |
| `ActiveWorkspaceRuntime`（`Vaeron.HelixStudio.Internal.Runtime`） | 角色 C 歸屬事件到哪個工作區的唯一依據——一個同步、無 Facade／Proxy 包裝的唯讀快取，由 `WorkspaceManagementService` 在每次 `LoadActiveWorkspaceAsync`／`SwitchActiveWorkspaceAsync` 成功時回填。存在的唯一理由是打斷遞迴：`IWorkspaceManagementFacade` 本身也被 `FacadeAuditProxy` 包住，若角色 C 為了取得工作區 id 而呼叫該介面，會反過來觸發一次新的攔截，變成「記錄一筆事件之前要先記錄一筆查詢工作區的事件」的無窮遞迴 |
| `AuditLogging`（本地文字檔，`%LocalAppData%\Helix-Studio\Logs\{date}.log`） | 角色 C 的另一個獨立輸出目標，與 EventLog 資料庫平行、不互相依賴——見下方對撞第 6 項 |

**收斂宣告：** 主動找過「每個工作區獨立日誌門檻」方向——`log_settings` 表為單列（`id = 1`），資料形狀確認是全域單一設定，非缺口而是刻意設計；也找過「事件記錄的權限分級」方向，程式碼與畫面均無此概念，排除。角色 C 加入初期曾採「完全繞過 MinLevel」設計，後因資料庫被大量 Info 級成功呼叫淹沒而修正為「固定排除 Info、Warning／Error 額外套用 MinLevel」，見主軸背景；也找過「無作用中工作區時事件該寫到哪」方向——結論是該次攔截在 EventLog 資料庫這條路徑上直接略過（`event_entry.workspace_id` 為必填、無合法值可寫），文字檔路徑不受影響仍會捕捉，非缺口而是既有 schema 的結構限制。

## 4. 需求

| 角色 | 會用到 | 需要 | 工作會用到 | 想要 |
|---|---|---|---|---|
| A 檢視操作者 | 清單、搜尋、嚴重度篩選、時間範圍篩選、展開細節、複製輸出 | 門檻提示 banner（知道為何某些事件看不到——僅適用角色 B 寫入的事件，角色 C 寫入的一律看得到）、日誌設定入口 | 追蹤工具安裝／啟動／停止歷史做故障排查；因終端使用場景為工廠現場，缺乏詳細操作記錄會構成責任歸屬問題 | 複製時有明確回饋（「已複製」提示） |
| B 事件寫入方 | 單一 `RecordEventAsync` 呼叫 | 寫入不阻塞主流程；門檻判斷由本主題內部處理，呼叫方不用先查等級 | 每個工具生命週期事件（安裝／啟動／停止／失敗）都留痕 | 不需要處理寫入失敗（現狀如此，不代表這是應然） |
| C 自動攔截寫入方 | `FacadeAuditProxy` 每次攔截時觸發一次 `EventLogAuditSink.CaptureAsync` | Info 一律不落地資料庫；Warning／Error 仍額外遵守 `MinLevel`；不阻塞被攔截的原呼叫（fire-and-forget，見 `FacadeAuditProxy.Dispatch`）；沒有作用中工作區時可以安靜略過（沒有「應該記但記不了」的錯誤感） | 全部 7 個 Feature、全部 Facade 方法呼叫中「有意義的」（失敗／例外）自動留痕，不依賴任何人記得呼叫 `RecordEventAsync` | 與本地文字檔（`AuditLogging`）平行寫入、互不依賴——不是「文字檔寫完才寫資料庫」的串接設計；文字檔不受這次收斂影響，仍捕捉全部呼叫 |

### 對撞

| # | 衝突 | 標記 |
|---|---|---|
| 1 | 「事件寫入失敗應可被追查」↔「全部呼叫方 fire-and-forget、無 try/catch」 | 衝突——寫入例外會直接中斷呼叫方（例如 `InstallToolAsync`）的方法執行，即使安裝本身已成功，使用者仍會看到與實際失敗原因無關的通用訊息（此衝突僅存在於角色 B 路徑；角色 C 路徑用 `Guard.RunAsync` 吞掉失敗，不會反過來中斷被攔截的原呼叫） |
| 2 | 「保留期限應持續生效」↔「清理只在 App 啟動時執行一次」 | 衝突——長時間不重啟應用程式時，過期事件不會被清除，保留期限形同虛設直到下次啟動（角色 C 寫入量遠大於角色 B，此衝突的影響隨自動攔截上線而放大） |
| 3 | 「日誌等級門檻」↔「多工作區各自獨立門檻」 | 不適用——確認為刻意的全域單一設定，非缺口 |
| 4 | 搜尋／嚴重度／時間範圍三個篩選同時作用 | 滿足——依序鏈式套用，互不衝突 |
| 5 | 「無資料」↔「篩選後無結果」 | 不適用——兩者刻意共用同一句「沒有符合條件的事件」，见第 10 段判準 |
| 6 | 「角色 C 該不該也套用 MinLevel 門檻」↔「角色 C 的需求是有意義的操作都要留痕（工廠責任歸屬）」 | 衝突已解——「有意義」不等於「全部」，成功的 Function 呼叫（Info）不是責任歸屬需要的訊號，固定排除；Warning／Error（實際失敗／例外）才是責任歸屬需要留痕的內容，額外仍套用 `MinLevel`，見主軸。`EventLogService.RecordAutomaticEventAsync` 是獨立於 `RecordEventAsync` 的第二個寫入方法,但兩者現在共用同一個 `MinLevel` 讀取（`LoadLogSettingsAsync`），差別只在角色 C 多一層 Info 的固定排除 |
| 7 | 「角色 C 寫入 EventLog 資料庫」↔「角色 C 也寫本地文字檔」是否該互相依賴 | 衝突已解——兩者是 `FacadeAuditProxy.Dispatch` 對每個已註冊 `IAuditSink` 各自獨立呼叫、各自獨立 `Guard.RunAsync` 吞例外,任一個沒註冊、寫入失敗或耗時都不影響另一個 |
| 8 | 「角色 C 需要工作區 id 才能寫 `event_entry`」↔「`IWorkspaceManagementFacade` 本身也被角色 C 攔截，若透過它取得工作區 id 會無窮遞迴」 | 衝突已解——改用 `ActiveWorkspaceRuntime`（同步唯讀快取，不經過 Facade／Proxy）取得，見第 3 段 |

### 對撞產生的新需求

無 —— 對撞未產生原清單外的需求，衝突 1、2 屬既有實作的缺口，非新需求；衝突 6、7、8 是角色 C 加入時的設計問題，已在實作階段解決，非遺留缺口。

### 本質

生命週期角度：`event_entry` 有兩種誕生方式——角色 B 呼叫 `RecordEventAsync` 且 `Severity >= MinLevel`（未達門檻時事件從未誕生，不是被隱藏）；角色 C 由 `EventLogAuditSink` 呼叫 `RecordAutomaticEventAsync`，`Severity` 必須不是 Info 且 `Severity >= MinLevel`、當下要有作用中工作區，三者同時成立才誕生（任一不成立，事件從未誕生，不是被隱藏）。存活期間無法被單筆刪除，只能整批消失於：保留期限清理（僅隨 App 啟動觸發）、或所屬工作區被刪除。事件本身是葉節點，死亡不拖累其他 Feature。

| 症狀 | 根因的哪一面 |
|---|---|
| 寫入例外中斷呼叫方主流程（僅角色 B）；保留期限只在啟動時生效一次 | 角色 B 把自己定位成「盡力而為的旁路記錄」，寫入方與清理排程都是單向、無回饋設計——這是角色 B 路徑既有的行為模式，角色 C 路徑刻意不繼承這個缺陷（用 Guard 吞例外、不中斷原呼叫） |

## 5. 功能清單

| # | 操作 | 觸發方式 | 做什麼 |
|---|---|---|---|
| 1 | 查詢事件清單 | 載入／外部呼叫 | 回傳指定工作區的事件，依時間新到舊排序 |
| 2 | 查詢日誌設定 | 載入 | 回傳全域最低等級／保留天數／匯出路徑，無資料列時回傳預設值（Info／30／null）而不寫入 |
| 3 | 查詢未讀數 | 載入 | 依工作區的已讀標記時間，計算之後新增的事件數 |
| 4 | 記錄事件（角色 B，手動） | 外部呼叫（其他 Feature 呼叫 `RecordEventAsync`） | 若嚴重度達門檻則寫入一筆事件，否則略過且視為成功 |
| 5 | 更新日誌設定 | 按鈕（Settings 畫面） | 覆寫全域日誌設定單列 |
| 6 | 標記已讀 | 導覽至事件頁面時觸發 | 寫入/更新該工作區的已讀時間為現在 |
| 7 | 刪除工作區時清理事件 | 外部呼叫（WorkspaceManagement 級聯） | 刪除該工作區所有事件與已讀標記 |
| 8 | 套用保留期限清理 | App 啟動時執行一次 | 刪除所有工作區中早於門檻天數的事件（`RetentionDays <= 0` 表示不清理） |
| 9 | 記錄事件（角色 C，自動攔截） | `FacadeAuditProxy` 攔截到任一 Feature 的任一 Facade 方法呼叫時自動觸發，無需業務程式碼呼叫任何函式 | `Severity` 為 Info（成功呼叫）一律略過；`Severity` 為 Warning／Error 時，若 `Severity >= MinLevel` 且有作用中工作區（`ActiveWorkspaceRuntime.CurrentId` 非 null）則寫入一筆事件；任一條件不成立則略過此次寫入（本地文字檔 `AuditLogging` 仍照樣捕捉全部呼叫，兩者互不依賴） |

## 6. 資料與狀態

### 資料形狀

**EventEntrySnapshot（對外契約）**

| 欄位 | 型別 | 必填 | 約束 |
|---|---|---|---|
| Id | int | 是 | 對應 `event_entry.id` |
| ToolName | string | 是 | 寫入時由呼叫方提供 |
| Severity | EventSeverity | 是 | Info／Warning／Error／None 四值 |
| Message | string | 是 | |
| Timestamp | DateTimeOffset | 是 | 寫入當下的 UTC 時間，不可變 |
| Command | string? | 否 | 可為 null |
| ExitCode | int? | 否 | 可為 null |
| Output | string? | 否 | 可為 null |
| HasDetails | bool | 是 | 衍生欄位，`Command`／`ExitCode`／`Output` 任一非 null 即為真 |

**RecordEventRequest**

| 欄位 | 型別 | 必填 | 約束 |
|---|---|---|---|
| WorkspaceId | int | 是 | |
| ToolName | string | 是 | |
| Severity | EventSeverity | 是 | |
| Message | string | 是 | |
| Command | string? | 否 | |
| ExitCode | int? | 否 | |
| Output | string? | 否 | |

**LogSettingsSnapshot**

| 欄位 | 型別 | 必填 | 約束 |
|---|---|---|---|
| MinLevel | EventSeverity | 是 | `None` 代表不記錄任何事件 |
| RetentionDays | int | 是 | 可選值：3／7／14／30／-1（-1 為永久保留，`<= 0` 視為不清理） |
| ExportPath | string? | 否 | 可為 null（尚未設定） |

**event_entry（內部資料表）**：欄位與 `EventEntrySnapshot` 一致，額外持有 `workspace_id`（外鍵，篩選用）；`severity` 於資料庫層以字串儲存，`timestamp` 以可排序字串格式（`yyyy-MM-dd HH:mm:ss.fffffffzzz`）儲存。

**log_settings（內部單列表）**：`id` 固定為 1；`min_level` 字串、`retention_days`、`export_path` 三欄與 `LogSettingsSnapshot` 一致。

**read_marker（內部資料表）**

| 欄位 | 型別 | 必填 | 約束 |
|---|---|---|---|
| workspace_id | int | 是 | 主鍵，每工作區至多一列 |
| last_read_at | DateTimeOffset | 是 | 以可排序字串格式儲存 |

### 狀態

**EventSeverity（枚舉，兼作記錄門檻）**

| 值 | 意義 | 進入條件 |
|---|---|---|
| Info | 一般資訊 | 呼叫方標記為 Info |
| Warning | 警告 | 呼叫方標記為 Warning |
| Error | 錯誤 | 呼叫方標記為 Error |
| None | 最高序位，代表「不記錄任何事件」，只作為 `MinLevel` 的可設定值，不會出現在任何一筆 `event_entry` 上 | 使用者在設定中選擇「不記錄任何事件」 |

**狀態轉換：** 事件記錄本身不轉換狀態（寫入即定形，唯讀直到被批次刪除），故無轉換表；`log_settings` 為單列覆寫，覆寫視為同一列的欄位更新，非狀態轉換。

### 讀寫

| 操作 | 讀 | 寫 |
|---|---|---|
| 查詢事件清單 | `event_entry`（依 workspace_id 過濾） | 無 |
| 查詢日誌設定 | `log_settings`（id=1） | 若不存在，僅回傳記憶體預設值，不寫入資料庫 |
| 查詢未讀數 | `read_marker`（該工作區）＋`event_entry` | 無 |
| 記錄事件 | `log_settings`（取得門檻做比對） | `event_entry` 新增列（僅當達門檻） |
| 更新日誌設定 | `log_settings` | `log_settings` 單列覆寫或新增 |
| 標記已讀 | `read_marker`（該工作區） | `read_marker` 單列覆寫或新增 |
| 刪除工作區時清理 | 無 | `event_entry`／`read_marker` 依 workspace_id 批次刪除 |
| 保留期限清理 | `log_settings`（取得保留天數） | `event_entry` 依時間早於門檻批次刪除，不分工作區 |

| 查詢日誌設定 | 無 | `LogSettingsSnapshot` |
| 更新日誌設定 | `LogSettingsSnapshot` | `(success, message)` |
| 依工作區清理事件（級聯用） | 工作區 id | 無回傳（`Task`） |
| 套用保留期限 | 無 | 無回傳（`Task`），內部依設定決定是否執行 |
| 訂閱異動通知 | 無（事件訂閱） | 任何寫入／設定變更／清理發生時觸發，不附帶內容 |

## 7. 失敗回饋

**失敗種類判準：重試同樣的輸入，結果會不會不同？** 會→可重試；不會→不可重試。

| 失敗 | 種類 | 使用者看到 | 呼叫方拿到 | 記事件 |
|---|---|---|---|---|
| 記錄事件時嚴重度低於門檻 | 不是失敗 | 無 | `(true, "已略過（低於目前日誌等級門檻）")` | 否 |
| `RecordEventAsync` 內部寫入資料庫時擲出例外（磁碟／鎖定問題） | 不可重試（呼叫當下的狀態已不可控） | 無事件日誌自身的訊息——例外沿呼叫鏈往上拋，若呼叫方（如 AppsManagement）本身也無 try/catch，最終由全域 `UnhandledAsyncError` 顯示「[失敗] 資料載入失敗」，與實際發生的寫入失敗無關 | 未被捕捉的例外 | 既有缺口——本應轉為 `(false, message)`，目前未做 |
| 更新日誌設定 | 本操作目前無任何驗證會失敗的路徑（無範圍檢查） | — | 恆為 `(true, "已更新")` | 否 |

**貫穿規則：** 所有成功／失敗訊息一律以 `ResultContract` 的 `Ok`／`Fail`（`"[失敗] "` 前綴）產生；但角色 B（事件寫入方）目前全數忽略回傳值，此契約對它們形同虛設。

| 情境 | 條件 | 該發生什麼 |
|---|---|---|
| 正常 | `Severity` 為 Warning 或 Error、且 `Severity >= MinLevel`、且有作用中工作區 | 寫入一筆事件，不觸發 `Changed`（見下方異常已修正列）；`Severity` 由攔截結果推導：例外→Error，`Result.Fail`→Warning，其餘→Info |
| 正常 | `Severity` 為 Info（成功呼叫） | 一律略過，不查 `MinLevel`、不查作用中工作區——Info 對角色 C 而言恆為噪音，固定排除 |
| 邊界 | `Severity` 為 Warning 或 Error，但低於使用者設定的 `MinLevel` | 略過此次寫入，與角色 B 的門檻判斷共用同一份 `LogSettingsSnapshot` |
| 邊界 | 沒有作用中工作區（例如全新安裝、尚未建立任何工作區時就有 Facade 呼叫發生） | 此次攔截在 EventLog 資料庫這條路徑上直接略過，不寫入、不報錯；本地文字檔（`AuditLogging`）路徑不受影響，仍會捕捉同一筆呼叫 |
| 邊界 | 同一筆呼叫同時有本地文字檔與 EventLog 資料庫兩個 Sink | 兩者各自獨立呼叫、各自獨立吞例外，任一個沒收到、寫入失敗或耗時，不影響另一個是否收到、何時收到 |
| 異常（已修正） | 不得觸發 `Changed`／`EventsChanged` | 見上方第 4 項行為規格新增列——若觸發會與畫面既有的「操作變化時重新整理」訂閱形成指數迴圈，此為角色 C 存在期間必須遵守的硬性限制，不是可選的效能優化 |
| 異常 | `EventLogAuditSink.CaptureAsync` 內部寫入資料庫時擲出例外 | 由 `Guard.RunAsync` 吞掉，不往上拋——不得影響被攔截的原呼叫的回傳值與時機，這是角色 C 與角色 B 最根本的差異 |
| 異常（已修正，曾在正式 App 實際發生） | `RecordAutomaticEventAsync` 若觸發 `Changed` | 會與 `MainShellViewModel.ApplyRefreshStatusBarAsync`（訂閱 `EventsChanged`，處理常式又呼叫 5 個同樣會被攔截的 Facade 方法）形成指數成長的迴圈——實測正式 App 啟動後數十秒內 `events` 資料表暴增到六千多筆、UI 卡死。修法：`RecordAutomaticEventAsync` 刻意不觸發 `Changed`（角色 B 的 `RecordEventAsync` 不受影響，仍會正常觸發），已用複製此訂閱模式的獨立測試專案重新驗證：修正後自動攔截零連鎖觸發，手動呼叫仍精準觸發一次 |

**跨操作互動：** 記錄事件與查詢事件之間沒有鎖定機制；因單一 UI 執行緒與 SQLite 單機存取，不構成真實並發問題。角色 C 的寫入是 fire-and-forget，不保證在被攔截的原呼叫返回前完成落地，因此即時查詢可能看不到「剛剛那一筆」——與第 8 段「不做事件記錄的即時推播」的既有非目標一致，不是新缺口。

## 10. 判準

| 判準 | 適用情境 |
|---|---|
| 「無資料」與「篩選後無結果」共用同一句空狀態文案是刻意簡化，不需要分開設計 | 前端呈現決策，兩者操作路徑相同（清空搜尋／篩選即可看到全部） |
| 事件寫入方（角色 B）呼叫 `RecordEventAsync` 一律不檢查回傳值 | 現況如此；若未來需要讓寫入失敗對使用者可見，屬於呼叫方（AppsManagement 等）藍圖的行為變更範圍，不在本主題內單方面修正 |
| 保留期限清理只在 App 啟動時執行一次，不是持續性背景排程 | 任何討論「保留期限是否即時生效」的前提 |
| 日誌等級門檻與保留天數是全域設定，不分工作區 | 任何討論「能否針對單一工作區調整記錄行為」的前提，答案是不能 |
`MinLevel` 對角色 B（`RecordEventAsync`）與角色 C（自動攔截，僅 Warning／Error）都生效；角色 C 的 Info 不受 `MinLevel` 值影響，永遠固定排除 | 任何討論「調低／調高日誌等級能不能減少事件清單筆數」的前提——調高 `MinLevel` 會同時濾掉角色 B 與角色 C 的低嚴重度事件；但把 `MinLevel` 調回 Info 也無法讓角色 C 的成功呼叫（Info）重新出現，那條路徑是固定排除，不是門檻可調整範圍內的值 |
| 角色 B 與角色 C 對同一個操作（例如安裝工具）會各自獨立寫入一筆，不去重 | 兩者是完全不同的寫入路徑（一個是業務程式碼手動呼叫，一個是攔截層自動觸發），刻意不做去重——去重需要先定義「同一個操作」的匹配規則，目前不存在這個概念 |
