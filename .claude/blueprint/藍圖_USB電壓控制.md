# 工程藍圖：USB 電壓控制

依據模板版本：v1.1

## 0. 依據與關係

| 既有藍圖 | 關係 | 說明 |
|---|---|---|
| 藍圖_事件日誌.md | 沿用 | 自動修正發生時呼叫 `EventLogFacade.RecordEventAsync` 記錄一筆 Info 事件，沿用其「事件寫入方 fire-and-forget、不檢查回傳值」的既有行為模式 |
| 藍圖_工作區管理.md | 無相關 | 本主題資料表（`usb_target_voltage`／`usb_global_setting`）均無 `workspace_id` 欄位，是全域跨工作區共用的設定，不受工作區切換或刪除影響——見第 10 段判準 |

## 1. 範圍與目的

**範圍：** USB 裝置電壓量測顯示、目標電壓設定與套用（手動／自動）、全域自動修正開關、裝置清單顯示。涵蓋 `UsbVoltageControlDomain`、`UsbVoltageControlRepository`、`UsbDeviceVoltageRepository`、`UsbVoltageControlDbContext`、`UsbVoltageControlView`／`UsbVoltageControlViewModel`。

**目的：** 避免連接的 USB 裝置因供電電壓偏離目標而斷線或提前進入休眠，讓操作者能設定每台裝置期望的電壓並監控偏離狀況。

**不做什麼：**
- 不做裝置的實體電壓量測與修正——現況為硬體通訊層尚未串接（見第 3、9 段）
- 不做依工作區區隔的電壓設定（設計上刻意全域共用）
- 不做已移除裝置的目標電壓記錄清理

## 2. 主軸

**目標電壓的設定與持久化，跟這個目標電壓是否真的被套用到實體硬體，是兩件事——前者永遠成立，後者目前恆為否。**

判準用法：任何提案問「它讓『設定被存起來』與『設定被真的套用』這兩件事的區隔更清楚，還是把兩者混為一談」，答不出來就不屬於這個主題。

## 3. 角色

| 角色 | 身分 | 為什麼是獨立角色 |
|---|---|---|
| A. 操作者 | 在 USB 電壓控制畫面切換自動修正、設定/套用目標電壓的人 | 需要驗證範圍、風險提示、依情境顯示的操作按鈕 |
| B.「USB 防休眠控制」已安裝工具 | Catalog 裡 `usb-anti-sleep` 對應的可執行工具，名稱固定為「USB 防休眠控制」 | 本主題的「服務是否運作中」（`IsServiceRunning`）完全依賴這個工具在 AppsManagement 裡是否正在執行，是被動查詢對象，不持有自己的需求 |

**往底下／外面／之間找過的：**

| 角色 | 從哪裡冒出來 |
|---|---|
| `UsbDeviceVoltageRepository`（硬體通訊樁） | 三個方法（列裝置／讀電壓／套電壓）目前全部寫死回傳失敗，訊息固定為「尚未串接硬體驅動介面（USB 電壓量測/修正的實際廠牌與 SDK 尚未決定）」——這是刻意標記的未完成邊界，不是隱藏的 bug |
| `DispatcherTimer`（5 秒輪詢） | 只有服務運作中且全域自動修正開啟時才觸發掃描，屬於過場時機角色 |
| `EventLogFacade` | 自動修正成功時記錄一筆 Info 事件，下游被動通知者 |
| `AppsManagementFacade`（`IsToolRunningByNameAsync`） | 決定 `IsServiceRunning`，本主題所有操作是否可用都間接依賴它，依賴方式是**名稱字串比對**（`"USB 防休眠控制"`），非 ID 關聯 |

**收斂宣告：** 主動找過「多裝置並發套用電壓」方向——`ApplyAutoCorrectScanAsync` 是循序 `foreach`，非並行，無並發問題；也找過「電壓設定是否該隨工作區切換」方向，資料形狀確認無 `workspace_id`，判定為刻意全域設計。無新方向。

## 4. 需求

| 角色 | 會用到 | 需要 | 工作會用到 | 想要 |
|---|---|---|---|---|
| A 操作者 | 開關全域自動修正、手動套用目標電壓、展開明細設定電壓（含 5/9/12/20V 預設按鈕） | 目標電壓範圍驗證（3–24V）、風險 banner、硬體狀態說明訊息 | 保護連接的 USB 裝置不因供電不穩而斷線或提前休眠 | 不支援電源管理的裝置要看得出來；套用按鈕依情境顯示或隱藏 |
| B「USB 防休眠控制」工具 | 被 `AppsManagement` 依名稱查詢是否執行中 | 名稱字串需與 Catalog 項目（`usb-anti-sleep`／「USB 防休眠控制」）精確一致 | 決定本畫面多數操作的可用狀態 | 無 —— 被動被查詢的一方，沒有主動需求 |

### 對撞

| # | 衝突 | 標記 |
|---|---|---|
| 1 | 「自動修正需要真的偵測與套用硬體電壓」↔「硬體通訊介面全部回傳失敗」 | 衝突——但屬刻意標記的現況（訊息明確說明廠牌/SDK 未決定），非缺口 |
| 2 | 「手動套用目標電壓」↔「`ApplyVoltageAsync` 必定回傳失敗」 | 衝突——`SetTargetVoltageAsync` 因此恆常回傳「已儲存但尚未實際套用」，功能上目前不會改變任何裝置的實際電壓，只會寫入資料庫 |
| 3 | 「自動修正計時器持續運作」↔「服務是否在跑靠工具名稱字串比對」 | 衝突——若 Catalog 工具名稱被改動，`IsServiceRunning` 會永遠為 false，連帶本畫面所有依賴它的操作停擺，且不會有任何錯誤訊息提示 |
| 4 | 風險 banner／自動修正開關的可用狀態都綁 `IsServiceRunning` ↔ `IsServiceRunning` 由另一個 Feature（AppsManagement）決定 | 滿足——刻意設計：服務程式必須真的在跑，操作才有意義 |
| 5 | 「裝置清單目前必為空」（硬體樁恆回傳空清單）↔「畫面沒有為空清單設計專屬文案」 | 衝突——`DataGrid` 沒有「尚未偵測到裝置」的空狀態訊息，僅靠上方硬體狀態 banner 說明，兩種情境（硬體未串接／硬體已串接但當下無裝置）在畫面上無法區分 |

### 對撞產生的新需求

無 —— 對撞未產生原清單外的需求，衝突 1、2、3、5 屬既有實作的現況與缺口，非新需求。

### 本質

生命週期角度：`usb_target_voltage` 誕生於第一次對某 `device_id` 呼叫 `SetTargetVoltageAsync`；存活期間沒有任何清理路徑——即使該裝置永久從系統移除，目標電壓記錄仍留在資料庫，不隨工作區刪除而清除（因為資料表本身無 `workspace_id`，不在 WorkspaceManagement 的級聯清除範圍內）。往下挖「為什麼電壓設定不分工作區」：USB 裝置是插在同一台實體電腦上的硬體，不因為邏輯上的「工作區（產線）」切換而改變，所以電壓目標全域共用是合理的架構決策，不是遺漏。但「已移除裝置的設定永久保留」目前看不出設計理由，兩者需要分開看待。

| 症狀 | 根因的哪一面 |
|---|---|
| 手動/自動套用永遠只達成「儲存」，硬體層永遠回報失敗 | 硬體通訊層是刻意留白的邊界樁，等待真實 SDK 決策——現況而非缺口 |
| 服務名稱字串比對脆弱、裝置清單無空狀態文案 | 這兩者都是「跨 Feature 依賴或跨情境判斷沒有做完整」的表現，屬於實作缺口 |

## 5. 功能清單

| # | 操作 | 觸發方式 | 做什麼 |
|---|---|---|---|
| 1 | 查詢裝置清單 | 載入／自動（`Changed`／`WorkspaceChanged`／`ToolsChanged` 觸發） | 回傳目前連接裝置＋各自量測電壓與目標電壓，附硬體介面狀態訊息 |
| 2 | 查詢全域自動修正開關 | 載入 | 回傳目前是否啟用 |
| 3 | 設定目標電壓 | 按鈕（手動輸入或預設值） | 驗證範圍後持久化，並嘗試即時套用到硬體 |
| 4 | 切換全域自動修正開關 | 按鈕 | 持久化開關狀態 |
| 5 | 自動修正掃描 | 計時器每 5 秒（僅服務運作中且開關啟用時） | 找出已連接、支援電源管理、且電壓超出容許誤差的裝置，逐一嘗試套用目標電壓並記錄事件 |

## 6. 資料與狀態

### 資料形狀

**UsbDeviceSnapshot（對外契約）**

| 欄位 | 型別 | 必填 | 約束 |
|---|---|---|---|
| DeviceId | string | 是 | 硬體層識別碼，目前恆為空清單（見第 9 段） |
| Name | string | 是 | |
| Kind | string | 是 | |
| Connected | bool | 是 | 現況實作固定為 `true`（只有連接的裝置才會出現在清單） |
| SupportsPowerControl | bool | 是 | 由硬體驅動回報 |
| LastInterruption | string | 否 | 預設空字串 |
| Voltage | double? | 否 | 量測值，硬體未串接時恆為 null |
| Target | double | 是 | 無設定記錄時預設 5.0V |
| IsWithinTolerance | bool | 衍生 | `Voltage` 非 null 且與 `Target` 差距 ≤ 0.15V |

**ApplyVoltageRequest**

| 欄位 | 型別 | 必填 | 約束 |
|---|---|---|---|
| DeviceId | string | 是 | |
| TargetVoltage | double | 是 | 3.0–24.0V，超出範圍拒絕 |

**usb_target_voltage（內部資料表）**

| 欄位 | 型別 | 必填 | 約束 |
|---|---|---|---|
| id | int | 是 | 主鍵 |
| device_id | string | 是 | 每裝置至多一列，無外鍵、無 `workspace_id` |
| target_voltage | double | 是 | 無範圍檢查於資料庫層，僅 Domain 層驗證 |

**usb_global_setting（內部單列表）**

| 欄位 | 型別 | 必填 | 約束 |
|---|---|---|---|
| id | int | 是 | 固定為 1 |
| auto_correct_enabled | bool | 是 | |

### 狀態

**服務運作狀態（衍生，非本主題持久化）**

| 值 | 意義 | 進入條件 |
|---|---|---|
| 運作中 | `IsServiceRunning = true` | AppsManagement 回報名為「USB 防休眠控制」的工具在目前作用中工作區執行中 |
| 未運作 | `IsServiceRunning = false` | 該工具未執行，或找不到作用中工作區 |

**狀態轉換：** 服務運作狀態不由本主題寫入，純粹讀取衍生，故無轉換表。目標電壓與開關為單值覆寫，非狀態機。

### 讀寫

| 操作 | 讀 | 寫 |
|---|---|---|
| 查詢裝置清單 | 硬體樁（恆回傳空）＋`usb_target_voltage`（僅在有連接裝置時才會用到，現況用不到） | 無 |
| 查詢自動修正開關 | `usb_global_setting`（id=1） | 無 |
| 設定目標電壓 | 無 | `usb_target_voltage` 覆寫或新增；並呼叫硬體樁套用（現況必定回報失敗） |
| 切換自動修正開關 | 無 | `usb_global_setting` 覆寫或新增 |
| 自動修正掃描 | `usb_global_setting`＋裝置清單（同上恆空） | 對超出容許誤差的裝置呼叫硬體樁套用（現況因裝置清單恆空，永遠不會真的執行到套用那一步）；成功時寫入 EventLog 一筆 Info 事件 |

### 對外能力

| 能力 | 輸入 | 輸出 |
|---|---|---|
| 查詢裝置清單與硬體狀態 | 無 | `(IReadOnlyList<UsbDeviceSnapshot> devices, string hardwareStatusMessage)` |
| 查詢全域自動修正開關 | 無 | `bool` |
| 設定目標電壓 | `ApplyVoltageRequest` | `(success, message)` |
| 切換全域自動修正開關 | `bool` | `(success, message)` |
| 執行自動修正掃描 | 無 | 修正裝置數（`int`） |
| 訂閱異動通知 | 無（事件訂閱） | 目標電壓／開關變更、或自動修正掃描有實際修正時觸發 |

## 7. 失敗回饋

**失敗種類判準：重試同樣的輸入，結果會不會不同？** 會→可重試；不會→不可重試。

| 失敗 | 種類 | 使用者看到 | 呼叫方拿到 | 記事件 |
|---|---|---|---|---|
| 設定目標電壓超出 3–24V 範圍 | 可重試（改成範圍內數值即可成功） | 「[失敗] 目標電壓須介於 3–24V 之間」 | `(false, message)` | 否 |
| 目標電壓已存入資料庫，但硬體樁套用失敗（現況恆定發生） | 不是真正的失敗——`success = true` | 「目標電壓已儲存，但尚未實際套用：尚未串接硬體驅動介面（...）」 | `(true, message)` | 否 |
| 硬體樁未來串接真實 SDK 後可能發生的實際套用失敗 | 未知——目前硬體樁只會回傳固定字串，尚無真實失敗語意 | 同上訊息格式，內容待硬體串接後才會不同 | 同上 | 否 |

**貫穿規則：** 硬體層目前沒有任何情境會讓 `SetTargetVoltageAsync` 整體回傳 `success = false`（除了範圍驗證），因為套用失敗被設計成「部分成功」訊息而非失敗——這代表現階段呼叫方無法單靠 `success` 判斷「硬體是否真的套用」，必須解析 `message` 文字。

### 空狀態與過渡

| 情境 | 呈現 |
|---|---|
| 無資料（裝置清單為空） | 沒有專屬空狀態文案——`DataGrid` 直接顯示為空表格，僅靠上方硬體狀態 banner 間接說明原因；既有缺口，見第 10 段判準 |

### 互動限制

## 9. 行為規格

> 逐項對應第 5 段，數量一致。

### 對應第 5 段第 1 項：查詢裝置清單

| 情境 | 條件 | 該發生什麼 |
|---|---|---|
| 正常 | 硬體樁已串接真實裝置（未來狀態） | 回傳實際連接裝置與量測電壓 |
| 現況 | 硬體樁尚未串接（目前狀態） | 恆回傳空清單＋固定的硬體未串接訊息 |
| 邊界 | 裝置有目標電壓記錄但裝置未連接 | 該裝置不會出現在清單（清單只列連接中的裝置），目標電壓記錄仍留在資料庫 |

### 對應第 5 段第 2 項：查詢全域自動修正開關

| 情境 | 條件 | 該發生什麼 |
|---|---|---|
| 正常 | 已有設定列 | 回傳實際值 |
| 邊界 | 尚無設定列（全新安裝） | 回傳 `false` |

### 對應第 5 段第 3 項：設定目標電壓

| 情境 | 條件 | 該發生什麼 |
|---|---|---|
| 正常 | 電壓在 3–24V 範圍內 | 持久化成功，觸發 `Changed`，嘗試套用硬體（現況必定「儲存但未套用」） |
| 異常 | 電壓超出範圍 | 直接拒絕，不寫入資料庫，不觸發 `Changed` |
| 邊界 | 同一裝置重複設定 | 覆寫既有列，非新增 |

### 對應第 5 段第 4 項：切換全域自動修正開關

| 情境 | 條件 | 該發生什麼 |
|---|---|---|
| 正常 | 任意布林值 | 持久化，觸發 `Changed` |
| 邊界 | 服務未運作時嘗試切換 | 前端已將開關 `IsEnabled` 綁 `IsServiceRunning`，UI 層面無法觸發；後端 Domain 本身沒有擋這個情境（若被繞過 UI 直接呼叫仍會成功寫入） |

### 對應第 5 段第 5 項：自動修正掃描

| 情境 | 條件 | 該發生什麼 |
|---|---|---|
| 正常 | 開關啟用、存在超出容許誤差且支援電源管理的已連接裝置 | 逐一嘗試套用目標電壓，成功者記一筆 Info 事件，回傳修正數 |
| 現況 | 開關啟用但裝置清單恆空（硬體未串接） | 每次掃描恆回傳 0，實際上沒有任何裝置會被處理到 |
| 邊界 | 開關未啟用 | 直接回傳 0，不查詢裝置清單 |
| 邊界 | 找不到作用中工作區（記事件時） | `LogEventAsync` 內部靜默略過，不記錄也不視為錯誤 |

**跨操作互動：** 計時器觸發的自動掃描與使用者手動套用可能同時作用於同一裝置；兩者都只是「寫入目標電壓／嘗試套用」，沒有互斥鎖，最後寫入者覆蓋前者，現況因硬體樁恆失敗而無實際硬體層面的競爭。

## 10. 判準

| 判準 | 適用情境 |
|---|---|
| 目標電壓與自動修正開關的資料表都沒有 `workspace_id`，是刻意的全域共用設計，不隨工作區切換或刪除而改變 | 任何討論「這個設定要不要分工作區」的前提，答案是不用——USB 裝置是實體硬體，不因邏輯工作區而變 |
| `IsServiceRunning` 完全依賴 AppsManagement 對「USB 防休眠控制」這個工具名稱的執行狀態查詢，是字串比對而非 ID 關聯 | 若日後 Catalog 工具改名，本主題會靜默失效（`IsServiceRunning` 恆為 false），排查此類問題時優先檢查名稱是否一致 |
| `SetTargetVoltageAsync` 的 `success = true` 不代表硬體真的被套用，需解析 `message` 判斷是否為「已儲存但未套用」 | 任何呼叫方或未來自動化測試判斷「電壓是否真的生效」時的前提 |
| 裝置清單目前恆為空、自動修正掃描恆回傳 0，是硬體樁未串接的現況，不是本主題邏輯的 bug | 排查「自動修正為什麼都沒有動作」時的第一個檢查點 |

## 11. 驗收條件

| # | 條件 | 怎麼證明 |
|---|---|---|
| 1 | 建置通過 | `dotnet build` 對 `Vaeron.HelixStudio.sln` 成功 |
| 2 | 目標電壓超出範圍時拒絕寫入 | 手動操作：輸入 25V 或 2V 並套用，預期收到「[失敗] 目標電壓須介於 3–24V 之間」，資料庫不新增/更新該裝置的記錄 |
| 3 | 裝置清單現況恆為空 | 讀碼確認 `UsbDeviceVoltageRepository.ListConnectedDevicesAsync` 回傳固定值 `(false, NotWiredMessage, [])`，執行畫面觀察表格為空、硬體狀態 banner 顯示對應文字 |
| 4 | 自動修正掃描在開關關閉時不查詢裝置清單 | 讀碼確認 `ApplyAutoCorrectScanAsync` 第一行檢查 `LoadGlobalAutoCorrectAsync`，為 false 時直接回傳 0，未呼叫 `LoadDeviceListAsync` |
| 5 | 服務未運作時自動修正開關在畫面上不可操作 | 手動操作：確保「USB 防休眠控制」工具未執行，觀察開關是否為停用狀態 |
