# 工程藍圖：Helix-Studio 本機資料庫共用層

## 定性

| 問題 | 回答 |
|---|---|
| 本質是什麼 | 一個獨立組件，持有 Helix-Studio 本機 SQLite 資料庫的三件事：資料庫檔案的位置、結構的套用、連線的提供。結構的唯一來源是打包在組件內的 `.sql` 指令碼；資料庫主題型別（`DbContext`）與主表映射型別日後一併放進本組件，功能組件只放 view 與查詢。 |
| 完整生命週期是什麼 | App 啟動 → `Paths.Local` 解析出資料庫檔案路徑 → 首次連線時 SQLite 依該路徑自建檔案 → 讀取 `__schema_history` 取得已套用的指令碼名稱 → 依檔名順序套用尚未套用者並逐一記錄 → 各功能組件經連線工廠取得連線讀寫。 |
| 現有最小結構能否表達 | 不能：新增最小結構，理由：`Net/Helix-Studio/` 底下沒有共用層目錄，三個既有專案（Kernel／Shell／App）沒有一個是「跨功能共用的資料主題」該待的位置——Kernel 是不引用任何工作區組件的葉，Shell 是單一功能，App 只做組裝。 |

## 主體順序

本藍圖採用**結構順序**（由下而上：路徑 → 結構來源 → 套用 → 對外表面 → 組裝），與既有 `藍圖_主視窗版面殼層.md` 同一種，全篇僅此一種。

## 骨架

依 vaeron-skeleton 分析器 VAE020–VAE023 所載的資料庫規則，固定順序：

| 順序 | 項目 | 內容 |
|---|---|---|
| 1 | 共用層目錄 | `Net/Helix-Studio/Shared/`，名稱取自 vaeron-skeleton `Workspace.props` 的 `SharedFolderName=Shared`。VAE021／VAE022 判定「共用層」就是看檔案路徑是否位於這個資料夾之下。 |
| 2 | `Vaeron.HelixStudio.Kernel/Paths.cs` | 自 `Vaeron.Kernel` 移植。資料庫檔案路徑是它的第一個真實呼叫點（`Paths.Local`）。註解所載「single-file 發佈時組件位置回傳空字串，故路徑不得由組件位置推導」正是本專案的發佈設定，原樣保留。 |
| 3 | `Shared/Vaeron.HelixStudio.Data` | 資料主題組件（`net10.0`）。對外表面：`IDatabaseFacade`（取得連線）、`DatabaseOptions`（檔案名稱）。`Internal/` 放結構套用與連線建立。 |
| 4 | `Shared/Vaeron.HelixStudio.Data/Schema/*.sql` | 結構的唯一來源，以 `EmbeddedResource` 打包。檔名以四位序號開頭決定套用順序。本次交付沒有任何一張業務表——畫面尚未給定，表跟著畫面進來，屆時新增一個 `.sql` 檔即可，不動任何程式碼。 |
| 5 | `Internal/SchemaApplier` | `CREATE TABLE IF NOT EXISTS __schema_history` → 讀出已套用名稱 → 以檔名排序的嵌入資源濾掉已套用者 → 逐一執行並寫入紀錄。 |
| 6 | `Internal/DatabaseFacade` | 委派連線建立；連線字串由 `Paths.Local` 與 `DatabaseOptions.FileName` 組出。 |
| 7 | `ServiceCollectionExtensions.AddHelixStudioData()` | 比照 `AddShell()` 慣例。`Composition.Register` 加入這一行，`Program.Main` 於建出容器後呼叫一次結構套用。 |

## 技術規範遵循

| 規範 | 是否符合 | 說明 |
|---|---|---|
| 禁止 Interface | 不適用 | 此 repo 無 `.claude/rules/` 規範文件。沿用 vaeron-skeleton 做法：`IDatabaseFacade` 用 interface，`Internal/` 實作類別 `internal sealed`。 |
| DI 統一用 primary constructor | 符合 | `DatabaseFacade(DatabaseOptions options)`、`SchemaApplier(IDatabaseFacade database)` 全部主建構子。 |
| VAE021 主表映射型別在共用層 | 符合 | 本組件即共用層。目前沒有主表；日後由映射工具自資料庫產生後放進本組件。 |
| VAE022 DbContext 在共用層 | 符合 | 同上。本次不建 `DbContext`——沒有任何實體型別，空的 `DbContext` 拿掉不改變任何結果，屬 §3.2 無效果的包裝。第一張表出現時，`DbContext` 與 EF Core 套件一併加入本組件。 |
| VAE023 不由 C# 定義結構 | 符合 | 結構寫在 `.sql`，C# 只負責讀出並執行，不推導、不比對模型。 |
| VAE020 查詢走 view | 不適用 | 本組件不含查詢；view 與查詢屬功能組件。 |
| 是否偏離 template/ 規範（＝污染） | 部分偏離，逐項列出理由 | (1) 本次只引用 `Microsoft.Data.Sqlite`，不引用 EF Core：沒有實體型別，EF Core 的每一項能力都沒有呼叫點。(2) 不建 `Schema` 以外的資料夾與不寫任何業務表：畫面尚未給定，先建表等於憑空發明需求，違反 §5.2。 |

## 驗收

| 項目 | 分析（我推導） | 驗證（外部系統實際跑過） |
|---|---|---|
| 建置通過 | — | `dotnet build Vaeron.HelixStudio.slnx` 0 警告 0 錯誤，四個組件全部產出 |
| 啟動後於 `Paths.Local` 產生資料庫檔案 | SQLite 連線開啟時自建檔案 | 已產生 `%LOCALAPPDATA%\HelixStudio\helix-studio.db`，12288 bytes，檔頭 `SQLite format 3` |
| `__schema_history` 存在且可查 | `CREATE TABLE IF NOT EXISTS` 先行 | 檔案位元組內含 `CREATE TABLE __schema_history (name TEXT PRIMARY KEY, applied_at TEXT NOT NULL)` |
| single-file 發佈後 SQLite 原生程式庫仍可運作 | — | 發佈版執行後行程存活、視窗標題為 `Helix Studio`。`Program.Main` 無 try-catch，原生程式庫載入失敗會在開窗前結束行程 |
| `build.ps1` 在已有 SDK 時不安裝、直接建置 | 版本帶比對命中即跳過安裝段 | 執行後建置成功、`.dotnet` 未被建立 |
| `build.ps1` 缺 SDK 時的安裝路徑正確 | — | 官方 `dotnet-install.ps1` 下載成功（76676 bytes），`-DryRun` 解析出 `dotnet-sdk-10.0.100-win-x64.zip` 與目標 `.dotnet`，`-NoPath True` 生效 |

未驗證清單（依賴外部系統精確行為、無法執行驗證的項目，逐條列出，是交付物的一部分）：
- 工廠現場電腦的使用者設定檔路徑若被群組原則重導向（漫遊設定檔、資料夾重導向），`Paths.Local` 解析出的位置會跟著改變，資料庫檔案是否仍可寫入取決於該環境的權限設定，本機無法代為驗證。
- 多個 Helix Studio 行程同時開啟同一個資料庫檔案時的鎖定行為：本次沒有並行寫入的呼叫點，未實際跑過。
- `build.ps1` 真正執行下載安裝的那一段只跑過 `-DryRun`：本機已有 .NET 10 SDK，無法在不破壞本機環境的前提下觸發實際安裝。已驗證的是下載可達、參數解析正確、目標路徑正確。
- 結構指令碼的套用只跑過「零個待套用」這條路徑：`Schema/` 目前沒有任何 `.sql`，第一張表進來時才會第一次跑到實際執行與寫入 `__schema_history` 的那段。

## 部署事實

`PublishSingleFile` 不內嵌原生程式庫。實測發佈成果為 15 個檔案，其中執行必要者為 `Vaeron.HelixStudio.App.exe`（126.1 MB，內含 .NET 10 執行環境）加六個原生 DLL：`e_sqlite3.dll`、`D3DCompiler_47_cor3.dll`、`wpfgfx_cor3.dll`、`PresentationNative_cor3.dll`、`PenImc_cor3.dll`、`vcruntime140_cor3.dll`。目標電腦不需安裝任何 .NET。
