# 工程藍圖：Helix-Studio 資料存取層

## 定性

| 問題 | 回答 |
|---|---|
| 本質是什麼 | 專案端不寫 SQL 字串。主表由映射工具自資料庫產生型別，功能組件以 LINQ 查 view 的 keyless 型別。SQL 只存在於 `.sql` 結構定義檔裡。 |
| 完整生命週期是什麼 | `.sql` 建庫 → 映射工具掃描資料庫產生型別 → 共用層持有 `DbContext` 與主表型別 → 功能組件各自貢獻自己那幾個 view 的 keyless 型別與查詢 → 顯示層拿投影。 |
| 現有最小結構能否表達 | 不能：目前的存取路徑是手刻 `SqliteConnection` 與字串常數 SQL，與 `.claude/rules/資料邏輯歸屬.md` 的分層（VAE021／VAE022／VAE023）不符。依 §4.1 屬結構選錯，整條重寫。 |

## 主體順序

本藍圖採用**結構順序**（由下而上：結構定義 → 型別產生 → 內容 → 查詢），與既有藍圖同一種，全篇僅此一種。

## 骨架

| 順序 | 項目 | 內容 |
|---|---|---|
| 1 | `.sql` | 結構的唯一來源。表、view、對照表內容全在這裡，是唯一容許出現 SQL 語法的地方。 |
| 2 | 映射工具 | `dotnet ef dbcontext scaffold` 掃描以 `.sql` 建出的資料庫產生型別。型別不由 C# 反推，改結構時重跑工具。 |
| 3 | `HelixStudioContext` | 共用層。持有全部表的映射型別。view 的型別不在這裡——那是各功能組件自己的事。 |
| 4 | `IModelParts` | 共用層定義的貢獻點。每個功能組件實作一份，把自己要用的 view 註冊成 keyless 型別。相依方向維持由功能組件指向共用層。 |
| 5 | 查詢 | 全部為 LINQ。過濾用 `Where`、模糊比對用 `EF.Functions.Like`、排序用 `OrderBy`，參數一律由 EF 綁定。 |
| 6 | 每列的字串 | 名稱、發行者、讀數字樣、摘要列的說明字串，全部是 `v_software_row` 的欄位。view 不吃參數，故可為靜態 view。 |
| 7 | 摘要 | 隨查詢條件變動的只有「幾個軟體」這個計數，以 LINQ 的 `Count` 取得。其餘取自 `v_machine_summary`，版面字串取自 `text_template`。 |

## 技術規範遵循

| 規範 | 是否符合 | 說明 |
|---|---|---|
| 資料邏輯歸屬 | 符合 | 見 `.claude/rules/資料邏輯歸屬.md`。分層依該檔的表：共用層 `DbContext` 與主表型別，功能組件 view 型別與查詢，顯示層只吃投影。 |
| VAE020 查詢走 view | 符合 | 功能組件只註冊 keyless view 型別，不註冊主表。 |
| VAE023 結構來源在資料庫 | 符合 | 型別由映射工具自資料庫產生。 |
| 值域不得被塌縮 | 符合 | LINQ 的 `Where` 是集合過濾，與 SQL 的 `WHERE` 同義，不塌縮值域。 |
| 是否偏離設計稿 | 無 | 存取方式不改變畫面。 |
