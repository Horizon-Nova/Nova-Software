# NetToolTestArea 功能盤點與畫面重新設計規劃表

整理來源：逐檔閱讀 `MainForm.cs`、`Views\*.cs`、`Services\*.cs`、`Utility\*.cs`、`Core\*.cs`、`app.manifest`。

目的：在重新設計畫面之前，把「現在到底有哪些功能、每個功能實際怎麼運作、哪些細節容易在重畫時被漏掉」寫清楚。重畫時請逐一對照每個功能的「操作流程」與「需保留的細節」，這些多半是現有程式碼裡沒有寫在畫面上、但拿掉會讓功能悄悄壞掉的行為。

專案位置：`tools\NetToolTestArea`（WinForms，.NET Framework 4.7.2，`app.manifest` 要求 `requireAdministrator`）

概況：7 個已接畫面的主功能分頁／1 個跨 3 個畫面共用的全域滑鼠鉤子／3 套互不相同的「找 InSpec 視窗」邏輯／6+ 個已寫好但沒有任何按鈕觸發的方法。

---

## 跨畫面共用注意事項

這些行為不屬於單一畫面，但同時影響好幾個畫面；只看單一分頁的程式碼會看不到。

### 共用的全域滑鼠鉤子（單例）

「點擊模式」「點擊視窗」「抓取視窗」三個畫面背後共用**同一個** `ClickModeUtility` 實例（`ServiceContainer` 建構時只 `new` 一次，分別注入給 `ClickModeService`／`ClickWindowService`／`CaptureWindowService`）。也就是說全應用程式同一時間只有一把系統層級的低階滑鼠鉤子（`WH_MOUSE_LL`）。

- 啟用其中一個模式時，若前一個模式還開著，`StartClickMode` 內部會先自動關閉舊的鉤子再裝新的——不會噴錯，但畫面上舊分頁的按鈕文字/顏色不會跟著變回「未啟用」。
- **切換分頁本身不會自動關閉**正在監聽的模式，只有整個視窗關閉（`MainForm.OnFormClosing`）才會強制關閉這三者。使用者可能啟用點擊模式後切去別的分頁，鉤子仍在背景監聽。
- 重畫畫面時建議決定：離開分頁要不要自動停用未關閉的擷取模式？

### 「找 InSpec 視窗」目前有三套互不相同的邏輯

| 使用位置 | 判斷方式 | 找不到時的退回規則 |
|---|---|---|
| 點擊模式／抓取單項 `ClickModeUtility.FindInSpecWindow()` | EnumWindows 掃所有可見視窗標題；先排除含 NetTool／測試區域／Cursor／Visual Studio／VS Code／.cs／.java／Chrome 字樣者 | 優先精準符合「InSpec 視窗版」→ 退回「InSpec for Windows」或單純「InSpec」→ 最後退回以類名 `InSpecAppFrame` 比對 |
| 函數分析（錄製）`MemoryInjectionUtility.TryGetInSpecTarget()` | 直接以行程名稱 `InSpec` 列舉行程，要求該行程有主視窗且標題含「InSpec 視窗版」 | 無退回規則，找不到即回傳失敗 |
| 觸發 Run 按鈕 `WmCommandCore.FindInSpecMainWindow()` | EnumWindows 找標題含「InSpec 視窗版」且視窗所屬行程名稱剛好是 `InSpec` | 無退回規則，找不到即回傳失敗 |

三套邏輯在 InSpec 視窗標題不是標準格式時，會給出不同的成功/失敗結果。重新設計建議收斂成一套共用判斷。

### 「可點擊」「容器」的類名清單是針對 InSpec 硬調校的

- **可點擊（`IsClickableClassName`）**：類名含 button／toolbar／tool／menu／link／label 關鍵字，或精確等於 `ToolbarWindow32`／`SysTabControl32`／`Static`／`SysLink`／`SysHeader32`
- **容器（`IsContainerType`）**：精確等於 `#32770`／`SysTabControl32`／`AfxMDIFrame100u`／`AfxFrameOrView100u`（後兩者是 MFC 應用程式特徵）
- 這份清單假設目標永遠是 InSpec（一個 MFC／舊式 Win32 UI 程式）。未來若要支援別的目標程式，這裡要跟著調整，不是通用規則。

### 查詢/篩選的實作方式不一致

「點擊模式」「點擊視窗」的查詢，是把目前記在記憶體的完整結果重新篩選、整批重建 DataGridView 內容；「抓取單項」「抓取視窗」的查詢，是直接切換既有列的 `Visible` 屬性。兩種對使用者的效果差不多，但實作路徑不同——重新設計時可以決定統一成一種。

### 系統管理員權限

`app.manifest` 要求 `requireAdministrator`，DLL 注入／全域鉤子等操作皆依賴此權限，重新設計時這個前提不能取消。

## 1. 點擊模式（已接畫面）

導覽按鈕文字：「點擊模式」　目的：點一下畫面上任何東西，抓出該控制項所在容器內「可點擊」的按鈕清單，並列出整個容器底下的完整控制項明細。

### 畫面元件

| 元件 | 型別 | 用途 |
|---|---|---|
| 左：檢測按鈕清單 | ListBox | 顯示本次找到的「可點擊」控制項；雙擊可測試點擊 |
| 查詢欄 | TextBox + 查詢按鈕 | 對右側明細表做子字串篩選（Enter 或按鈕皆可觸發） |
| 啟用點擊模式 | Button（切換態） | 灰＝待機／綠＝監聽中，文字同步切換「啟用⇄停用」 |
| 狀態列 | Label | 顯示是否找到 InSpec 視窗、已讀取幾個控制項等即時狀態 |
| 右：明細表 | DataGridView | 欄位：#編號、句柄ID、視窗標題、類名、文字內容、WM_COMMAND ID |

### 操作流程

1. 按「啟用點擊模式」→ 嘗試尋找 InSpec 視窗（找到/找不到都會繼續，只是狀態文字不同）→ 掛上全域滑鼠鉤子 → 按鈕轉綠、文字變「停用點擊模式」。
2. 使用者在螢幕任何位置點一下滑鼠左鍵（**系統全域**，不限定 InSpec 視窗範圍）→ 鉤子擷取游標下的控制項。
3. 由該控制項向上找「容器」（往上最多 10 層，找到符合容器類名者為止）；同時取得該控制項的頂層視窗。實際操作目標＝容器優先，其次頂層視窗，最後才是原始控制項本身。
4. 對目標遞迴列出**全部**子控制項（不限深度），連同目標本身的資訊一起塞進右側明細表。
5. 左側清單則另外計算：若剛剛點到的控制項本身就是「可點擊」類型 → 清單只放這一個；否則若找到容器 → 列出容器內所有「可點擊」子控制項。
6. 狀態列顯示讀到幾個控制項，**點擊模式自動關閉**（單次擷取，不是持續監聽）。
7. 可在查詢欄輸入文字即時篩選右側明細（比對句柄十六進位、視窗標題、類名、文字內容、WM_COMMAND ID 任一欄）。
8. 雙擊左側清單中的項目 → 依類名決定用「工具列點擊」（模擬座標點擊）或「標準按鈕點擊」（`BM_CLICK`）方式送出點擊，成功/失敗會跳訊息視窗。

### 依賴的 Service / Utility

`ClickModeService`、`ClickWindowService`、`WindowApiService`

### 需保留的細節 / 邊界情況

- **單次擷取**：不是持續監聽模式，抓到一次點擊就自動停用，要再抓一次得重新按「啟用」。
- **全域範圍**：滑鼠鉤子是系統全域的，點擊 NetTool 自己的視窗也會被擷取（沒有排除自身視窗，靠使用者自己別點到自己）。
- 與「點擊視窗」「抓取視窗」共用同一把鉤子，見上方跨畫面注意事項。
- 左側面板初次顯示時會把 SplitContainer 分割線置中（僅第一次生效，之後使用者手動拖曳的位置會被尊重）。

## 2. 點擊視窗（已接畫面）

導覽按鈕文字：「點擊視窗」　目的：與「點擊模式」介面幾乎一樣，但操作粒度是「整個視窗」而不是「容器」——點一下就抓出整個頂層視窗底下的所有控制項。

### 與「點擊模式」的差異

| 項目 | 點擊模式 | 點擊視窗 |
|---|---|---|
| 擷取目標 | 容器（往上找到 #32770／SysTabControl32 等） | 永遠是頂層視窗（`GetAncestor(GA_ROOT)`） |
| 是否查找 InSpec 視窗 | 會（影響狀態列文字） | 不會，直接處理被點到的視窗 |
| 左側清單來源 | 容器內可點擊子控制項 | 整個視窗全部子控制項中「可點擊」者 |
| 按鈕/狀態文字 | 啟用/停用點擊模式 | 啟用/停用點擊視窗 |

明細表欄位、查詢篩選方式、雙擊測試點擊、單次擷取後自動停用、共用滑鼠鉤子等行為，與「點擊模式」完全相同，不重複列出。

### 依賴的 Service / Utility

`ClickWindowService`、`WindowApiService`

## 3. 抓取單項（已接畫面）

導覽按鈕文字：「抓取單項」　目的：不靠滑鼠點擊，直接讀出 InSpec **選單列**（menu bar）的完整項目樹，取得每個選單項的 WM_COMMAND ID。

### 畫面元件

| 元件 | 型別 | 用途 |
|---|---|---|
| 查詢欄 | TextBox + 查詢按鈕 | 依子字串切換既有列的顯示/隱藏（非重建清單） |
| 抓取選單項 | Button（單次動作，非切換態） | 觸發一次完整選單掃描 |
| 明細表 | DataGridView | 沿用五欄schema，但實際只有「文字內容」＝選單路徑、「WM_COMMAND ID」有意義，其餘三欄固定填「-」 |

### 操作流程

1. 按「抓取選單項」→ 狀態列「查找 InSpec 視窗中...」→ 找不到就跳警告視窗並中止（提示確認 InSpec 已開啟、標題含「InSpec」）。
2. 找到後狀態列「正在讀取選單項...」→ 走 `GetMenu` → 逐一 `GetSubMenu` 遞迴到底（葉節點＝沒有子選單），組出「檔案 > 開啟」這種選單路徑字串，記下每個葉節點的 WM_COMMAND ID。
3. 0 個選單項 → 跳警告視窗並中止；否則填入明細表，狀態列顯示筆數。

### 需保留的細節 / 邊界情況

- 不是「模式切換」按鈕，是單次觸發的動作按鈕，沒有啟用/停用兩態。
- 查詢是切換既有列 `Visible`，與「點擊模式/點擊視窗」的查詢實作方式不同。
- **欄位名不符實際內容**：明細表沿用控制項用的五欄（句柄ID/視窗標題/類名/文字內容/WM_COMMAND ID），但選單項本質上只有「選單路徑」與「WM_COMMAND ID」兩個有意義的值，其餘三欄永遠是「-」——重新設計時建議給選單清單專屬欄位。

## 4. 抓取視窗（已接畫面）

導覽按鈕文字：「抓取視窗」　目的：點一下視窗，把整個視窗底下所有控制項（不只可點擊的）攤平列出——沒有左側清單、沒有雙擊測試點擊，是單純的「檢視用」抓取工具。

### 畫面元件與流程

| 元件 | 用途 |
|---|---|
| 抓取視窗控件（切換態按鈕） | 灰＝待機／綠＝監聽中；點擊任一視窗後擷取，成功後自動停用 |
| 明細表（單一） | 句柄ID／視窗標題／類名／文字內容／WM_COMMAND ID 五欄皆有意義（與抓取單項不同） |
| 查詢欄 | 切換既有列可見度（與抓取單項同一種實作方式，與點擊模式/點擊視窗不同） |

1. 啟用後點擊任一視窗 → 解析其頂層視窗祖先（沒有就用被點到的控制項本身）。
2. 遞迴列出該頂層視窗底下**全部**子控制項，填入明細表；0 個控制項則跳警告視窗。
3. 自動停用抓取模式。

### 依賴的 Service / Utility

`CaptureWindowService`、`WindowApiService`

### 需保留的細節 / 邊界情況

與「點擊模式」「點擊視窗」共用同一把全域滑鼠鉤子（見跨畫面注意事項），單次擷取後自動停用的行為一致。

## 5. 函數分析（已接畫面・內部機制最複雜）

導覽按鈕文字：「函數分析」　目的：把 DLL 注入 InSpec 行程、掛上 API Hook，即時錄下操作期間呼叫了哪些 API/訊息，並輸出成報告；另外可單獨觸發 InSpec 的「Run」功能。

### 畫面元件

| 元件 | 用途 |
|---|---|
| 開始錄製 / 停止錄製 | 互斥切換（開始時停止鍵才會啟用），錄製上限 10 秒會自動停止 |
| 觸發 Run（使用 SendMessageW） | 獨立按鈕，與錄製無關，直接送出寫死的 WM_COMMAND 給 InSpec 的 Run 按鈕 |
| 函數列表 | DataGridView：函式／函式名稱／DLL 名稱／地址／時間——**只在錄製中即時由日誌解析出來**，不是查詢結果 |

### 「觸發 Run」流程

1. 用 `WmCommandCore.FindInSpecMainWindow()` 找主視窗（見跨畫面差異表，這套邏輯沒有退回規則）。
2. 用**寫死的 WM_COMMAND ID `0x000080B5`**（程式註解記載是先前分析 output.txt 得出）嘗試取得 Run 按鈕控制項句柄（作為 lParam），再送出 `WM_COMMAND`。
3. 成功/失敗跳訊息視窗。

### 「開始錄製」流程

1. 產生內部動作名稱 `錄製_yyyyMMdd_HHmmss`（**目前畫面上完全看不到這個名稱**，只會寫進最終 output.txt 的「動作 :」欄位）。
2. 找 InSpec 目標行程（狹義規則，見跨畫面比較表）→ 檢查 `InSpecHookDLL.dll` 是否已注入 → 未注入則注入（最多重試 2 次、每次間隔 1 秒驗證）。
3. 開一個具名管道伺服器 `InSpecHookDLL_LogPipe` 非同步接收注入 DLL 傳回的 UTF-16 日誌行，並對目標行程啟用 API Hook。
4. 10 秒計時器啟動，逾時自動觸發「停止錄製」。
5. 錄製期間，日誌逐行解析：只處理含 `[API]` 或 `[HOOK]` 標記的行（`[DLL] [UPDATE_TIME]` 開頭的行會被忽略），解析出函式名稱／視窗類名／標題／句柄／訊息碼等，依函式名稱去重（同名會更新既有列而不是新增列）。

### 「停止錄製」流程

1. 計算錄製時長，關閉 API Hook 與具名管道連線。
2. 把整段錄製期間收集到的 API 呼叫，依時間排序後**去重輸出**：同一筆 API 呼叫出現 2～10 次會合併只印一次；超過 10 次則印一次並註記「(出現 N 次，已省略重複)」。
3. 寫入／附加到 `《目前工作目錄》\output.txt`（**不是**應用程式安裝目錄或 AppData，是行程啟動當下的 current directory，會隨啟動方式不同而變）。

### 需保留的細節 / 已知風險

- **API 監控寫死開啟**：`StartRecording(enableApiMonitor: true, ...)` 的 `true` 是常數；程式內殘留「勾選『啟用 API 監控』」之類的提示文字，但畫面上**已經沒有對應的核取方塊**了——這是過時字串，重新設計時要清掉或補回對應控制項。
- **Run 按鈕 ID 是寫死常數**，依賴特定版本 InSpec 的按鈕 ID 不變；若 InSpec 改版導致 ID 變動，這裡只會回報「發送失敗」，不會告訴使用者是 ID 對不上。
- 函數列表 DataGridView 的內容**完全是暫存的**：只反映「這次」錄製，切分頁再切回來不會保留、也不會重新載入（`RefreshView()` 是空函式）。
- output.txt 寫在目前工作目錄而非固定位置，重新設計時可考慮固定輸出資料夾。

## 6. 金鑰工具（已接畫面・授權邏輯，改動需謹慎）

導覽按鈕文字：「金鑰工具」　目的：讀取／手動輸入本機硬體指紋，計算或驗證授權金鑰——這是另一套 `LicenseService` 授權邏輯的**對照測試工具**，門檻值、權重、演算法、鹽值都必須與正式授權服務保持一致。

### 畫面元件

| 區塊 | 元件 | 用途 |
|---|---|---|
| 左：指紋輸入 | 8 個輸入列 | ModuleId、GUID key（必填）、CPU ProcessorId、SMBIOS UUID、BIOS 序號、主機板序號、C: 卷序號、實體網卡 MAC——皆可手動編輯 |
| 左：指紋輸入 | 讀取本機 | 用 WMI/登錄檔即時偵測本機硬體值，回填上方欄位（讀完仍可手動再改） |
| 右：金鑰結果 | 總分／門檻／底線 摘要列 | 即時顯示評分，依通過/可重綁/不足變色（深綠／橘／紅） |
| 右：金鑰結果 | 待驗證金鑰欄 | 貼上或顯示 `GUID:HASH` 格式金鑰 |
| 右：金鑰結果 | 產生金鑰／驗證金鑰／複製金鑰 | 三個動作按鈕 |
| 右：金鑰結果 | 結果明細框 | 唯讀多行文字，列出每個指紋的加權明細（有效/無效/缺失＋配分） |

### 評分規則（必須與 LicenseService 完全一致，不可單獨調整）

| 指紋 | 權重 |
|---|---|
| CPU ProcessorId | 30 |
| SMBIOS UUID | 20 |
| BIOS 序號 | 15 |
| 主機板序號 | 15 |
| C: 卷序號 | 10 |
| 實體網卡 MAC | 10 |

總分 ≥ **60** 為「通過」；40～59 為「可重新綁定但未通過」；<40 為「不足」。指紋值若為空白，或落在已知佔位字串黑名單（如「To Be Filled By O.E.M.」、全 F/全 0 的 GUID 等）則視為**無效**不計分。

### 操作流程

1. **讀取本機**：即時查詢本機 WMI/登錄檔，回填 6 個指紋欄位（不含 ModuleId、GUID key）。
2. **產生金鑰**：以目前畫面上的 ModuleId + GUID key（必填，空白會報錯「GUID 不可為空白」）+ 6 個指紋欄位「目前顯示的值」（不會重新去讀 WMI）計算 SHA-256（依標籤排序的有效指紋 + ModuleId + GUID + 內部鹽值），輸出大寫十六進位雜湊；最終金鑰格式為 `GUID:HASH`，同步顯示分數是否達到通過/可重綁門檻。
3. **驗證金鑰**：解析貼上的 `GUID:HASH`（驗證 GUID 格式、雜湊需恰好 64 碼十六進位字元），用目前畫面上的指紋欄位重新算一次雜湊，以**常數時間比對**（手刻 XOR 迴圈，因為 .NET Framework 4.7.2 沒有框架內建的 `CryptographicOperations`）比對是否相符，回報四種狀態之一：格式無效／金鑰正確且可授權／金鑰正確但分數不足／金鑰不正確。
4. **複製金鑰**：複製「上一次產生金鑰」的結果到剪貼簿（不是驗證欄位的內容），金鑰為空時會提示失敗。

### 需保留的細節 / 已知限制

- 權重、門檻（60/40）、鹽值 `HorizonNova-InSpecTool-Salt-v2`、雜湊演算法（SHA-256＋分隔符 0x1F）都是與另一套正式 `LicenseService` 「必須保持一致」的雙生實作——重畫畫面不能只看這個工具本身，改動前要先確認正式服務端是否同步。
- ModuleId 留白時視為「一般金鑰模式」，填寫時代表金鑰綁定到特定模組/功能，兩者輸出的雜湊不同（同一組指紋＋不同 ModuleId 會產生不同金鑰）。
- 「複製金鑰」只認得產生金鑰的結果，跟驗證金鑰是各自獨立的狀態，容易被誤會成同一份。

## 7. IsolatedStorage 測試（已接畫面）

導覽按鈕文字：「IsolatedStorage」　目的：手動測試 .NET Framework 的 `IsolatedStorageFile`（User+Assembly 範圍）能否跨重啟持久化一個路徑字串，是規格驗證用畫面，不是終端使用者功能。

### 畫面元件

| 元件 | 用途 |
|---|---|
| CurrentTargetPath 欄 | 使用者輸入／顯示目前存在 IsolatedStorage 裡的路徑字串 |
| 保存 Target | 把欄位內容寫入 IsolatedStorage（`InSpecTool\current-target.txt`） |
| 讀取 Target | 從 IsolatedStorage 讀回，**無條件覆蓋**目前欄位內容 |
| Input 內容欄 | 預帶文字「這是測試寫入內容。」，供「附加寫入」使用 |
| 刪除 Target | 刪除 IsolatedStorage 內的檔案 |
| 刷新狀態 | 重新顯示診斷文字（等同重新呼叫 RefreshView） |
| 附加寫入 Target | 把「Input 內容」附加寫入**目前已保存**的 CurrentTargetPath 所指向的真實檔案系統路徑 |
| 結果框 | 唯讀多行文字：Scope/Directory/File/Exists/StoredTarget 診斷資訊 |

### 行為細節（容易搞混的地方）

- **切分頁 / 刷新狀態**：只有在 CurrentTargetPath 欄位**目前是空白**時才會自動從 IsolatedStorage 回填，不會覆蓋使用者正在輸入、尚未保存的值。
- **讀取 Target 按鈕**：行為不同——無論欄位目前有沒有內容，都會被 IsolatedStorage 裡的值覆蓋。
- **附加寫入 Target**：不是寫入畫面上顯示的路徑文字，而是重新去讀「已保存」的 IsolatedStorage 值當作真實檔案路徑操作（若從未保存過會拋出「目前沒有可用的 CurrentTargetPath」）——這是刻意設計，用來驗證「重開程式後，之前存的路徑是否還能正確讀回並使用」。
- 設計上的測試協定就寫在畫面提示文字裡：「先保存 CurrentTargetPath，再用附加寫入驗證程式重開後是否仍可讀回。」

## 已知限制與待決事項

- **整個工具需要系統管理員權限**（`app.manifest` 的 `requireAdministrator`）——DLL 注入、全域滑鼠鉤子等操作都依賴這個前提，重新設計時不能取消。
- **函數分析的「API 監控」目前無法關閉**：程式碼寫死 `enableApiMonitor: true`，但介面上殘留「勾選『啟用 API 監控』」等提示文字，實際畫面上沒有對應核取方塊——文字與畫面已經不同步。
- **觸發 Run 依賴寫死的 WM_COMMAND ID**（`0x000080B5`），綁定特定版本 InSpec 的按鈕識別碼，換版風險没有對應的偵測/提示機制。
- **output.txt 輸出位置是行程當下的工作目錄**，不是固定的應用程式資料夾，重新設計時可考慮固定輸出位置。
- **三套「找 InSpec 視窗」邏輯**與**兩種查詢/篩選實作方式**目前並存（見「跨畫面共用注意事項」），重新設計是收斂成一套的好時機。
- **金鑰工具的評分規則屬於雙生實作**，任何調整都必須同步檢查正式 `LicenseService` 是否也要跟著改，不能只改這個測試工具。
- **抓取單項畫面沿用了不適合的五欄 schema**（見該功能章節），重新設計時建議給選單清單專屬欄位配置。
