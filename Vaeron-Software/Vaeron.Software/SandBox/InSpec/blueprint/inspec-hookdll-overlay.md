## 1. 範圍與目的

**標的識別（避免命名混淆）：**

| 項目 | 事實 |
|---|---|
| 本標的 | Micro-Vu Corporation「InSpec for Windows」光學量測軟體（版本資源 CompanyName、簽章 CN=Micro-Vu Corporation of California） |
| 非本標的 | Chef/Progress「Chef InSpec」（Ruby 合規稽核工具），僅名稱相同，無任何關聯 |
| 技術棧 | C++ / MFC100（VS2010, vc100）/ x86 32-bit |
| 安裝路徑 | `C:\Program Files (x86)\Micro-Vu Corporation\InSpec for Windows` |

**範圍：** 對 InSpec for Windows 執行期進行 HookDLL 注入，於不修改原始安裝的前提下，提供：(1) 量測完成時以視覺打勾覆蓋摘要面板數值；(2)「元素」清單右側量測工具列下方新增 Demo 按鈕。兩者共用同一注入/監看執行緒/建置基礎設施，同屬一個功能主題（執行期 UI 覆蓋）。

**目的：** 現場量測員需要在量測完成時一眼判斷「通過」，不需逐一判讀摘要數值；InSpec 原生摘要面板不提供這種一眼可辨的完成指示，故以執行期覆蓋層補足。

**不做什麼：**
- 不修改 InSpec 原始檔案（`.exe`／資源 DLL）
- 不子類化 InSpec 原生控制項
- 不將完成判斷改為事件驅動（已反編譯確認輪詢語義正確，見第 4 節「本質」）

## 2. 主軸

**完成訊號出現時，覆蓋層必須正確反映該訊號並取代/疊加對應畫面元素，且全程不修改、不子類化 InSpec 原生控制項，Disable 後完全還原不留殘跡。**

判準用法：任何提案問「它讓覆蓋層在不侵入 InSpec 原生行為的前提下正確反映完成狀態嗎」，答不出來就不屬於這個主題。

## 3. 角色

| 角色 | 身分 | 為什麼是獨立角色 |
|---|---|---|
| A. 現場量測員 | 使用 InSpec 進行光學量測的終端使用者 | 只在意結果一眼可辨，不理解也不需理解底層機制 |
| B. HookDLL 開發/維護者 | 撰寫、建置、部署 HookDLL 的工程角色 | 需要開關能力、可還原保證、明確建置規格 |
| C. InSpec 進程本身 | 被注入的目標執行期程序 | 穩定性是硬約束——覆蓋層出錯不可拖垮它 |

**往底下／外面／之間找過的：**

| 角色 | 從哪裡冒出來 |
|---|---|
| InSpec 摘要對話框（`#32770` 內 GXWND/1268、值 1266、旗標 1264） | 執行期動態重建，非模板控制，座標與 class 由程式碼決定——不是普通的「畫面」，是需要專屬錨定手法的目標 |
| 監看執行緒（MonitorThread） | 生命週期獨立於 InSpec 主執行緒，輪詢驅動顯示與定位邏輯，是覆蓋層存活的唯一輸入來源 |
| 注入器（32-bit 進程限制） | InSpec 為 32-bit，注入器位元數不符會取得錯誤的 kernel32 位址，是獨立於 HookDLL 本身邏輯之外的部署約束 |

**收斂宣告：** 已考慮並排除兩個替代方向——(1) 編輯 `InSpecRes_cht.dll` 資源模板：因摘要控制項為執行期重建，模板編輯對其無效；(2) 改用事件驅動判斷完成：反編譯確認 InSpec 本身未提供完成事件，1264 可見性只是面板刷新函式的副作用，輪詢是唯一可行手法且語義已驗證正確（見第 4 節「本質」）。主動找過其餘方向（例如子類化控制項截取繪製訊息）無新方向——已排除，因子類化直接違反角色 C 的穩定性約束。

## 4. 需求

| 角色 | 會用到 | 需要 | 工作會用到 | 想要 |
|---|---|---|---|---|
| A. 現場量測員 | 摘要面板畫面 | 完成時清楚視覺指示 | InSpec 量測流程本身 | 不被無意義數值干擾 |
| B. 開發/維護者 | HookDLL 匯出函式、dumpbin | Enable/Disable 開關、可還原保證、明確建置規格 | 32-bit 建置工具鏈 | 改動不破壞 InSpec 原始安裝 |
| C. InSpec 進程 | 被注入 HookDLL | 覆蓋層獨立子視窗、不子類化 | — | 不因覆蓋層邏輯崩潰 |

### 對撞

| # | 衝突 | 標記 |
|---|---|---|
| 1 | A 需要「完成時大打勾覆蓋」 ↔ B 需要「不改 InSpec 原始安裝」 | 滿足——執行期注入取代靜態資源編輯 |
| 2 | B 需要「可關閉並完全還原」 ↔ C 需要「不可因改動崩潰」 | 滿足——覆蓋層為獨立子視窗，非子類化，Disable 即銷毀 |
| 3 | Demo 按鈕需要跟隨版面變化定位 ↔ InSpec 對外無版面變化事件通知 | 衝突→本質 |
| 4 | 完成訊號判斷需要準確 ↔ InSpec 對外無完成事件通知 | 衝突→本質 |

### 對撞產生的新需求

無 — 對撞逼出的手法（輪詢＋錨點重找）已完整反映於第 5 節功能清單，未產生原清單外的新操作。

### 本質

生命週期角度：覆蓋層／Demo 按鈕誕生於對應 Enable 匯出呼叫；存活需要監看執行緒每 300ms 的輪詢持續驅動（顯示/隱藏判斷、位置重算）；死亡於對應 Disable 呼叫（銷毀子視窗、清旗標）；死亡不拖累 InSpec 本身，因覆蓋層與 Demo 按鈕皆為獨立子視窗而非原生控制項的一部分。

根因（對撞 3、4 共同指向）：InSpec 對外不提供任何事件通知機制（無版面變化事件、無量測完成事件），且摘要控制項於執行期動態重建。這使得任何整合都只能靠「控制項 ID 錨定 + 輪詢」，無法走事件訂閱路線。

反編譯（Ghidra）進一步確認了完成訊號（control 1264）的本質：

| 層 | 函式（RVA 相對 InSpec.exe imagebase 0x60000000） | 職責 |
|---|---|---|
| L5 量測引擎 | `FUN_602961d0` | 狀態轉換後呼叫 L4 |
| L4 完成派發 | `FUN_601a13d0` | 呼叫 L3；成功則觸發後續動作 |
| L3 面板刷新（核心） | `FUN_601a1430` | 迭代元素容器、逐一呼叫面板更新；容器非空且非重入時才執行 |
| L1 面板更新 | `FUN_6022bba0`（摘要頁）／`FUN_6021e9e0`（點頁） | 末端對指示器物件（offset +0x94/+0x98）無條件呼叫 `ShowWindow(SW_SHOW)` |

| 事實 | 內容 |
|---|---|
| control 1264 的本質 | 不是專用完成旗標，是面板刷新函式每次執行時無條件 `ShowWindow` 的副作用 |
| 未完成不顯示的原因 | 元素容器為空 → L3 早退 → 面板從不刷新 → 1264 從未被 SHOW |
| 完成語義 | per-element（當前元素已量測），非整批完成 |

| 症狀 | 根因的哪一面 |
|---|---|
| 資源 DLL 編輯對摘要控制項無效 | 執行期動態重建，模板僅為版面佔位參考 |
| Demo 按鈕需每 tick 重新定位 | InSpec 無版面變化事件通知 |
| 完成訊號借用 1264 可見性而非專屬旗標 | InSpec 本身未提供完成事件，只能借用其刷新副作用 |

**結論：** 「輪詢 1264 可見性」語義上等於「追蹤當前元素已量測」，語義正確且穩定，不需改為事件驅動（見第 10 節判準）。

## 5. 功能清單

| # | 操作 | 觸發方式 | 做什麼 |
|---|---|---|---|
| 1 | 啟用摘要打勾覆蓋 | 外部呼叫匯出 `EnableSummaryPatch`（經 `ThreadWrapper_EnableSummaryPatch` 供 `CreateRemoteThread`） | 設定 `g_overlayEnabled`，確保監看執行緒運作中 |

## 6. 資料與狀態

### 資料形狀

**全域旗標**

| 欄位 | 型別 | 必填 | 約束 |
|---|---|---|---|
| `g_overlayEnabled` | BOOL | 是 | 摘要打勾覆蓋開關 |
| `g_demoEnabled` | BOOL | 是 | Demo 按鈕開關 |

### 狀態

**監看執行緒生命週期**

| 值 | 意義 | 進入條件 |
|---|---|---|
| Idle | 未啟動 | 兩旗標皆為 false |
| Running | 300ms 週期輪詢中 | 任一旗標為 true |

**狀態轉換：**

| 從 | 到 | 觸發 | 不可逆 |
|---|---|---|---|
| Idle | Running | 任一 Enable 匯出被呼叫 | 否 |
| Running | Idle | `StopMonitorIfIdle` 偵測兩旗標皆為 false | 否 |

### 讀寫

| 操作 | 讀 | 寫 |
|---|---|---|
| 摘要打勾顯示邏輯 | `GetDlgItem(dlg, 1264).IsWindowVisible` | 覆蓋層 `ShowWindow(SW_SHOWNA)` / `ShowWindow(SW_HIDE)` |
| 覆蓋層錨定 | class=`GXWND` 且 `GetDlgCtrlID`==1268 之視窗，其 `GetParent` | 覆蓋層建立於該摘要 `#32770` 之下 |
| Demo 按鈕定位 | `ToolbarWindow32`（id 1166）之 rect，`ScreenToClient` 至父面板 | 覆蓋層 `SetWindowPos`（bottom+20, 148×22） |

### 對外能力

| 能力 | 輸入 | 輸出 |
|---|---|---|
| 啟用/停用摘要打勾覆蓋 | 無 | `g_overlayEnabled` 狀態變更、監看執行緒生命週期連動 |
| 啟用/停用 Demo 按鈕 | 無 | `g_demoEnabled` 狀態變更、監看執行緒生命週期連動 |
| 遠端執行緒包裝（`ThreadWrapper_*`） | 無（`DWORD WINAPI` 簽章，供 `CreateRemoteThread` 呼叫） | `DWORD` |

## 7. 失敗回饋

**失敗種類判準：重試同樣的輸入，結果會不會不同？**

| 失敗 | 種類 | 使用者看到 | 呼叫方拿到 | 記事件 |
|---|---|---|---|---|
| 錨點（GXWND/1268 或 ToolbarWindow32/1166）暫時找不到 | 可重試 | 覆蓋層/Demo 按鈕不顯示，InSpec 本身不受影響 | 無（監看執行緒下一輪 300ms 自動重試） | 否 |
| 遠端模組基址無效 | 不可重試（需重新注入） | 無反應 | 無 | 否 |
| DLL 被載入中的 InSpec 鎖住，重建無法覆蓋輸出 | 不可重試（需先關閉 InSpec 程序） | 建置失敗 LNK1104 | 建置錯誤訊息 | 否 |
| 建置時未連結 `gdi32.lib` | 不可重試（需修正建置腳本） | 連結錯誤（GDI 函式未解析符號） | 建置錯誤訊息 | 否 |
| 建置時未加 `/utf-8` | 不可重試（需修正建置腳本） | 原始碼中 CJK 字串字面值被 cp950 誤讀，字串內容或相鄰宣告損毀 | 編譯異常或執行期亂碼 | 否 |
| 64-bit 進程執行注入器 | 不可重試（需改用 32-bit 注入器） | 無反應或存取違規 | 注入失敗 | 否 |

**貫穿規則：** 任何錨點或遠端模組基址無效時，絕不計算位址並呼叫，避免存取違規拖垮 InSpec 進程。

## 10. 判準

| 判準 | 適用情境 |
|---|---|
| 完成訊號一律沿用 InSpec 自身 `GetDlgItem(dlg,1264).IsWindowVisible`，不逆向或新增專屬完成旗標 | 任何需要判斷「量測是否完成」的新功能 |
| 任何錨點或遠端模組基址無效時，絕不計算位址並呼叫 | 涉及遠端呼叫或動態尋找 UI 控制項的功能 |
| 顯示改造一律走執行期 HookDLL 注入，不編輯 UI 資源 DLL（`InSpecRes_cht.dll`）模板 | 摘要面板或其他執行期動態重建控制項的改造 |
| 新增覆蓋/按鈕類功能沿用同一監看執行緒 + 獨立旗標模式，不另開執行緒 | 新增第三種覆蓋層或注入式 UI 元件時 |
| `SetTimer(NULL, id, …)` 會忽略指定 id、回傳系統自配 id，必須用回傳值比對 `WM_TIMER` 的 `wParam`，`KillTimer` 亦用回傳值 | 任何新增計時器邏輯 |
