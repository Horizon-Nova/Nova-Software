# VNCSCP 基本功能驗證（UltraVNC 檔案傳輸服務）

走 UltraVNC 伺服器本身、需要密碼的檔案傳輸服務，不開檢視器視窗。用 `probe\`（反射叫出 VNCSCP 既有的 `RfbFileTransferClient`，不是另寫一套）對真的伺服器實測。舊版 VNCSCP 已在 2026-10-15 刪除（git 的 b76deee 還有），probe 不能再跑；協定改由 `tools/VNCSCP/Rfb.cs` 實作並實測。

- 日期：2026-10-14
- 伺服器：VM `VNC-Server`（UltraVNC 1.8.3.0，`uvnc_service` 服務，172.18.100.169:5900，RFB 003.008）
- 用戶端：主機（zh-TW，ANSI 950/Big5）
- 遠端投放區：`C:\test\dropzone`

## 結果

| 功能 | 結果 | 證據 |
|---|---|---|
| 連線＋VNC 驗證 | 通過 | security types 17,117,2 → 選 2（VNC Auth）→ security result 0 |
| 傳單一檔案 | 通過 | `hello.txt` 送達，56 bytes、內容逐位元組相符 |
| 傳資料夾（英數檔名） | 通過 | `plainfolder` 伺服器自動解壓成 `plainfolder\a.txt`、`plainfolder\sub\b.txt`，`!UVNCDIR-plainfolder.zip` 解完即移除 |

結論：連線、傳檔、傳英數資料夾三項的「走 UltraVNC 服務傳輸」路線已驗證可行。資料夾自動解壓是 UltraVNC 伺服器收到 `!UVNCDIR-*.zip` 時自己做的，不必額外送指令。

## 中文資料夾：實驗紀錄（結論：不是單純 zip 編碼選錯）

兩端編碼其實相同：
- 伺服器（VNC-Server）：GetACP 950、OEMCP 950、系統地區 zh-TW。
- 主機：ACP 950。

既然兩端都是 950，就不是地區設定對不上。接著用他們既有的上傳程式，換 zip 內部項目名的編碼、換上傳檔名，逐項測：

| # | 送什麼 | zip 內項目名編碼 | 上傳檔名 | probe 回報 | 伺服器結果 |
|---|---|---|---|---|---|
| 1 | 英數資料夾 `plainfolder`（真 `FromDirectoryAsync`） | Big5(950) | `!UVNCDIR-plainfolder.zip` | SUCCESS=True | **解壓成功**，含子目錄，zip 移除 |
| 2 | 中文資料夾 `測試資料夾`（真 `FromDirectoryAsync`） | Big5(950) | `!UVNCDIR-測試資料夾.zip` | SUCCESS=True | 未解壓，留下 263 bytes zip |
| 3 | 預製 zip（中文內部檔名）當檔案上傳 | UTF-8 | `!UVNCDIR-測試資料夾.zip` | SUCCESS=True | 未解壓，留下 261 bytes zip |
| 4 | 預製 zip（中文內部檔名）＋ASCII 檔名 | UTF-8 | `!UVNCDIR-folderX.zip` | SUCCESS=False | 未上傳成功、未解 |
| 5 | 預製 zip（中文內部檔名）＋ASCII 檔名 | Big5(950) | `!UVNCDIR-folderY.zip` | SUCCESS=False | 未上傳成功、未解 |

觀察：
- 只有 #1（檔名與內容全英數）整條過。
- #2、#3：上傳檔名帶中文，zip 內部無論 Big5 或 UTF-8，伺服器都不解，只留 zip。
- #4、#5：把中文內容包進 ASCII 檔名的 zip，反而連傳輸都回失敗（SUCCESS=False）。

所以中文失敗不是「zip 內部項目名編碼選錯、換一下就好」。牽涉到 UltraVNC 1.8.3 檔案傳輸對非 ASCII 的整體處理（可能新版改用 UTF-8 檔名協定、要先協商 FT 版本），黑箱換編碼兜不出來。

**可靠的下一步**：用真正的 UltraVNC Viewer 把一個中文資料夾送到同一台伺服器，看它成不成、怎麼送（抓它實際送出的 FT 版本協商與檔名位元組），拿來對照。使用者記得「中英文都可以」，若成立，真 Viewer 的位元組就是答案。這一步要開 Viewer 的實際畫面操作。

（原本以為是 `ZipFile.CreateFromDirectory(..., 本機 ANSI)` 把 zip 項目名寫成 Big5、換成 UTF-8 就好；#3 證明單換 zip 項目名編碼無效，推翻這個假設。）

## 其他要修的問題（讀程式時發現、尚未實測）

來自 `VNCSCP` 原始碼，本次沒測（只測了小檔與小資料夾），移植成 HelixStudio 工具前要補測與修正：
- 驗證交握沒有套在 3 秒逾時內：伺服器收了 TCP 卻不回版本橫幅時會卡住，「全部測試」逐台跑會整串停。
- 整個檔案或 zip 用 `ReadAllBytesAsync` 一次讀進記憶體；單次傳輸只有 60 秒逾時：大檔必失敗。
- 收到 length ≥ 5,000,000 的封包不讀掉內容，之後資料流會錯位。
