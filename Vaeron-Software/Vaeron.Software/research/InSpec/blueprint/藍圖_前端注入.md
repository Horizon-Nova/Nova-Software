# 前端注入 藍圖

## 1. 定位
把我方的 UI 元件（完成小圖示覆蓋層、就地編輯欄位、工具列按鈕）用 `CreateWindowEx` 建在 InSpec 自己的視窗上,證明可直接改造 InSpec 前端——元件是 InSpec 行程內的真實子視窗,不是外部應用疊在上面,也不是我方軟體另開一個控制台代管 InSpec 的 UI。
依據規格：無正式規格;打勾覆蓋層沿用舊藍圖 `summary-checkmark.md`／`inspec-hookdll-overlay.md`,本檔以技術分類重新收斂。

**本輪修正（使用者三次連續糾正後定案）：** 先前版本的打勾覆蓋層蓋滿整個摘要對話框,跟「輸入值直接可編輯」這個需求在畫面上互搶同一塊區域。定案：覆蓋層縮小成只蓋住完成小圖示（id `1264`）本身的範圍;摘要面板的「輸入值」那一行改成真正的 Win32 `Edit` 控制項疊在原本 GDI 畫字的位置,使用者直接點進去打字,不是我方另開一個面板或按鈕去代理修改。

## 2. 範圍
- 涵蓋：監看執行緒維護四種注入元件——完成小圖示覆蓋層（含樣式/顏色/文字自訂）、輸入值就地編輯欄位、Demo 按鈕、即時讀寫（LiveEdit）按鈕。
- 排除：注入底座（→ `藍圖_dll注入`）、按鈕點下後填提示的機制（→ `藍圖_訊息注入`）。

## 3. 資料模型
錨點/旗標：
- 摘要對話框 ← GXWND id `1268` 的父視窗;完成指示 ← id `1264` 可見＝完成
- 輸入值文字行 ← 既有 GDI 捕捉確認的固定座標 `x=50,y=55`（GXWND client 座標),就地編輯欄位建在 `x=48,y=52,w=240,h=18`,略微內縮蓋住原字左邊界
- 工具列錨點 ← `ToolbarWindow32` id `1166`（Demo/LiveEdit 按鈕放其下方;就地編輯欄位寫回時也用它觸發重新執行）
- 開關旗標（各自獨立,共用一條監看執行緒）：`g_overlayEnabled`（同時控制小圖示覆蓋層＋就地編輯欄位,兩者是同一個「改前端顯示」能力的兩個部分,不分開開關）／`g_demoEnabled`／`g_liveEditEnabled`

## 4. 資料交換
覆蓋層／就地編輯欄位本身無自訂契約——注入的是視窗,不是資料。就地編輯欄位的「目前值」來源：`Hooked_TextOutW`/`Hooked_ExtTextOutW` 在 IAT hook 內順手快取 x=50 且 y∈[53,58] 的文字進 `g_lastValueText`（不需要每次都呼叫 `CaptureGxwndPaint` 強制重繪）,`TickValueEdit` 在欄位沒有 focus 時同步顯示。寫回走既有 `藍圖_訊息注入` 的 `AutoFillAndConfirmPrompt`。

## 5. 端點與流程
監看執行緒 `MonitorThread`（`SetTimer` 300ms tick）：每 tick 跑 `TickOverlay`／`TickValueEdit`／`TickDemoButton`／`TickLiveEditButton`,依旗標建立/銷毀對應子視窗
- 完成小圖示：`TickOverlay` → 用 `GetDlgItem(dlg, SUMMARY_DONE_ID)` 取小圖示的 `GetWindowRect`,把 `SummaryOverlayProc` 視窗只蓋住那塊小範圍（不再是整個對話框),`DrawOverlaySymbol` 依 `g_overlaySymbolMode`（打勾/叉叉/自訂文字)畫出來,顏色走 `g_overlaySymbolColor`
- 輸入值就地編輯：`TickValueEdit` → `FindSummaryGrid()` 找到 GXWND 作父視窗,`CreateWindowExW(WS_EX_CLIENTEDGE, L"Edit", ...)` 建在固定座標,`SetWindowLongPtrW(GWLP_WNDPROC, ValueEditSubclassProc)` 子類化以攔截 `WM_KILLFOCUS`／Enter 鍵。使用者離開欄位或按 Enter → `CommitValueEdit` → 若「輸入提示」對話框未開,先 `ClickToolbar1165ButtonByIndex(0)` 觸發重新執行（InSpec 沒有原地改值介面,改值等於重新回答一次提示)→ 等對話框出現 → `AutoFillAndConfirmPrompt(新值)` 寫入並確認
- LiveEdit 按鈕：`TickLiveEditButton` → 在錨點工具列下方 `CreateWindowEx(LiveEditButtonProc)`;點下 → `LiveEditPopupProc` 彈我方輸入框（建在 InSpec 行程內）→ 填值送 `AutoFillAndConfirmPrompt`
匯出開關：`EnableSummaryPatch`/`DisableSummaryPatch`（同時控制小圖示＋就地編輯欄位)、`SetOverlaySymbolMode`/`SetOverlayColor`/`SetOverlayCustomText`（樣式自訂,整數/字串走 `ThreadWrapper_*` 直傳或既有字串傳遞慣例)、`EnableLiveEditButton`/`DisableLiveEditButton`、`EnableDemoButton` → 設旗標 → `EnsureMonitorThread`/`StopMonitorIfIdle`
程式碼：`InSpecHookDLL.cpp`（`MonitorThread`／`Tick*`／`ValueEditSubclassProc`／`CommitValueEdit`／`RememberValueTextIfMatch`／`LiveEditButtonProc`／`LiveEditPopupProc`／`RegisterMonitorClasses`）
Host 端 UI：`InSpecHookDLLHost\MainWindow.xaml` ②執行卡片內「InSpec 摘要面板前端改造」區塊——一個啟用開關 + 樣式/顏色選擇,不是獨立控制台,樣式只決定完成小圖示長怎樣,數值編輯本身直接發生在 InSpec 自己的畫面上。

## 6. 業務規則
- 四元件共用一條監看執行緒 + 各自旗標;`StopMonitorIfIdle` 只在旗標全關才停執行緒。
- 完成小圖示與就地編輯欄位共用同一個 `g_overlayEnabled` 旗標,`EnableSummaryPatch`/`DisableSummaryPatch` 同時控制兩者的建立/銷毀,理由：對使用者跟對商務展示而言是同一個能力（改前端顯示),不需要兩個各自的開關製造混淆。
- 元件是 InSpec 行程內子視窗（`g_hSelfModule` 為 hInstance）,跟隨 InSpec 生死;DLL 卸載時 `DllMain` DETACH 呼叫 `Disable*` 清掉。
- 就地編輯欄位使用者正在打字時（`GetFocus() == g_valueEdit`）不用快取值覆蓋顯示內容,避免使用者輸入到一半被蓋掉。
- 字面 CJK 直接寫（build `/utf-8`）;舊 `DemoButtonProc` 註解提的 `\u` 轉義不再沿用。

## 7. 權限
需注入（`藍圖_dll注入`）。授權：原廠口頭同意「改造 InSpec 前端」。

## 8. 跨功能依賴
- 依賴：`藍圖_dll注入`（子視窗建在 InSpec 行程內）、`藍圖_訊息注入`（LiveEdit 按鈕寫提示值）。
- 被誰用：VaeronInSpecDemo「前端注入 Demo」開關;展示「我方能改 InSpec 前端」這條能力。

## 9. 已知限制／待決定／修正記錄
- 打勾 overlay＋Demo 按鈕：前序 session 已實機驗證（舊藍圖）。
- LiveEdit 按鈕：本 session 新增,已 build;`?` 端到端（按鈕出現→彈窗→寫值→提示更新）尚未完整實機重跑確認。
- overlay 無 `WS_EX_TRANSPARENT` → 可見時擋住覆蓋區滑鼠;不影響現流程（編輯入口是另開的按鈕,非 overlay 內點擊）。
- **摘要面板輸入值就地編輯：已撤回（2026-07-30 使用者定案）。** 先前版本做過（Edit 控制項疊在 GXWND 輸入值行）並實機驗證過寫回鏈路，但使用者後續明確要求「摘要不可編輯，只需改樣式」——可編輯能力改放到 X/Y/Z 座標。`TickValueEdit`／`CommitValueEdit`／`ValueEditSubclassProc`／`RememberValueTextIfMatch` 已從程式碼移除，`g_overlayEnabled` 現在只控制完成小圖示的樣式覆蓋層，不再涉及任何 Edit 控制項。這條紀錄保留是誠實記錄「做過又撤回」，不是還在進行中的工作。
- **X/Y/Z 座標就地編輯 ＋ 重新載入蒙版：兩者都有「結構/功能正確，但視覺不出現」的已確認限制（2026-07-30 實機驗證）。**
  結構面確認過的事實：`EnumChildWindows`／`GetWindow(GW_CHILD)` 直接查證，兩者建立的子視窗都真實存在、`IsWindowVisible=true`、Z-order 在 `InSpecAppFrame` 直接子視窗中排最前（`GetWindow(main, GW_CHILD)` 回傳的第一個就是我方視窗）、尺寸與目標區域（X/Y/Z 三個 `Static` 控制項的真實 rect；蒙版對齊 `AfxMDIFrame100u` 的完整內容區 rect）精確吻合，不是猜測座標。
  功能面確認過的事實：X 欄位輸入新值、離開焦點後，`GetWindowTextW` 直接讀真實 `Static id=19000` 控制項，確認文字已經真的變成使用者輸入的內容（`SetWindowTextW` 寫回成功，不是我方另外疊一份假資料）；重新載入蒙版觸發時，`WM_COMMAND(32920)`（元素→重新量測）確實送達 InSpec 並至少一次觀察到 X 值變化（5000.0000），證明真實動作有發生。
  **視覺面未能確認：** 多次在觸發後立即截圖（含把動畫時長暫時延長到 15 秒排除時間差因素），螢幕上完全看不到就地編輯欄位的白底/框線、也看不到蒙版的「重新載入中」文字與抖動點——即使同一時間點查詢視窗狀態顯示 `visible=true`、Z-order 正確。推斷（尚未驗證，列為推測不列為結論）：`InSpecAppFrame` 這個 MDI 主框架底下、圍繞 X/Y/Z 即時座標讀值的自繪機制可能用類似 `GetDC`+直接繪圖、不透過標準 `WM_PAINT`／`InvalidateRect` 週期的方式頻繁重繪，導致它在畫面合成層級蓋掉我方子視窗的像素，即使子視窗本身在 Z-order／訊息處理層級仍然存在且正常運作（滑鼠點擊命中測試、鍵盤輸入都正常，因為那是作業系統依 Z-order 判斷，跟實際畫面合成是兩件事）。
  **可能的修法方向（尚未實作，需使用者決定是否投入）：** 把這兩個子視窗改成獨立的頂層（`WS_EX_LAYERED`＋`WS_EX_TOPMOST`）視窗，不當作 `InSpecAppFrame` 的子視窗——頂層視窗由 DWM 合成，不受 InSpec 內部繪圖機制影響，但需要額外追蹤 `InSpecAppFrame` 的位置/大小變化來同步覆蓋層座標，複雜度比現有作法高。
